# 10 — Delivery, Definition of Done, and Release Gates

## 1. Required delivery contents

The final project delivery MUST contain:

```text
README.md
Makefile
src/
include/
tests/
testdata/ or tests/fixtures/
docs/
examples/
```

Equivalent organization is acceptable, but all required categories must be clearly identifiable.

Required content:

- all C17 production source/header files;
- build instructions;
- CLI usage documentation;
- repository format documentation matching actual implementation;
- JSON/YAML config examples;
- full automated tests;
- golden fixtures/vectors;
- randomized test tooling;
- crash/fault injection tests;
- corruption fixtures or generators;
- acceptance traceability matrix mapping catalog IDs to tests;
- no required generated binary artifacts unless explicitly included as convenience extras.

## 2. Build gate

PASS only if:

- clean build succeeds from delivered source;
- mandatory production executable is `darc`;
- C production build does not require prohibited third-party libraries/runtimes;
- warnings treated/documented at an appropriately strict level;
- no unresolved symbols or stubbed mandatory functions.

## 3. Algorithm gate

PASS only if project-owned implementations exist and pass tests for:

- Buzhash64 CDC;
- SHA-256;
- CRC-32C;
- LZ77;
- canonical Huffman;
- JSON parser;
- YAML subset parser;
- Robin Hood hash index;
- Merkle trees;
- XOR parity recovery.

A wrapper around an external implementation is a failure.

## 4. Repository-format gate

PASS only if:

- canonical object types serialize/deserialize;
- immutable object CIDs verify;
- deterministic golden bytes pass;
- refs/HEAD publish atomically;
- index is rebuildable;
- format/version errors are handled.

## 5. Snapshot gate

PASS only if:

- recursive scan works;
- include/exclude config works;
- metadata captured;
- chunks deduplicate;
- duplicate independent files remain independent on restore;
- hardlink topology preserved in full restore;
- parent/incremental fast path works without contaminating canonical objects with inode/device identity;
- snapshot deletion removes only the published ref, handles HEAD deterministically, and leaves reclamation to GC;
- snapshot statistics are correct;
- zero/large/non-ASCII files work.

## 6. Diff/reporting gate

PASS only if:

- A/D/M/P/T/H classifications are correct;
- chunk reuse metrics are correct;
- path filtering works;
- text output meets readability contract;
- JSON and NDJSON are valid/structured;
- standalone SVG is valid and deterministic for fixed input.

## 7. Restore gate

PASS only if:

- full restore reproduces logical tree, bytes, required metadata, symlinks, hardlinks;
- partial restore works;
- overwrite policies behave exactly;
- path traversal/symlink escape is prevented;
- corrupt chunks are never silently emitted;
- restored file full hash is verified before final publication.

## 8. Integrity/recovery gate

PASS only if:

- quick/full/scrub verification work;
- raw and compressed corruption are detected;
- missing single protected chunk is recovered by parity and CID-verified;
- two missing members in a stripe are declared unrecoverable;
- bad parity with healthy data is regenerated by explicit repair;
- corrupt index is safely rebuilt;
- final status/exit codes are correct.

## 9. Crash-safety gate

PASS only if required crash checkpoints prove:

- old snapshots remain valid;
- partial new snapshots are not visible;
- published snapshots survive derived-index interruption;
- stale journal/temp state is recognized;
- GC interruption never deletes live-only bytes before replacement state is durable.

## 10. Garbage-collection gate

PASS only if:

- reachability across all refs and snapshot parents is correct;
- dry-run performs zero mutations;
- unreachable objects are reclaimed;
- live objects are retained;
- affected parity stripes are safely repacked;
- repository verifies after GC;
- historical retained snapshots restore after GC.

## 11. Configuration gate

PASS only if:

- JSON and YAML examples normalize identically;
- CLI > file > repo default > built-in precedence works;
- invalid syntax/types/unknown keys fail clearly;
- required parser edge cases pass;
- config influences every documented subsystem where applicable.

## 12. Test gate

PASS only if:

- all mandatory catalog cases are implemented;
- traceability matrix is complete;
- mandatory automated suite passes;
- randomized/reference-model suite passes for documented seeds/count;
- stress suite passes;
- no mandatory test is ignored/xfail/disabled.

## 13. Documentation gate

PASS only if docs accurately describe:

- build;
- command usage;
- config schema/subset;
- repository layout;
- object encodings;
- algorithms/parameters;
- error/exit codes;
- test commands;
- recovery behavior;
- limitations/non-goals.

Documentation that claims behavior not actually wired into production is a gate failure.

## 14. Definition of Done

The task is DONE only when all mandatory Release Gates above pass and all required deliverables are present.

The following do NOT qualify as completion:

- "core features implemented" while recovery/GC/config/reporting/tests remain incomplete;
- a CLI with commands that print TODO/not implemented;
- mocked repository state;
- placeholder manifests;
- hard-coded golden outputs;
- passing unit tests while required E2E/corruption/crash tests are absent;
- an archive that restores ordinary files but ignores required metadata/hardlinks;
- detection without required bounded recovery;
- recovery without cryptographic verification;
- GC that has not been crash-tested;
- JSON support without YAML support or vice versa;
- text reports without required machine/SVG outputs.

## 15. Stop condition

Implementation work may stop and completion may be claimed only after:

1. all mandatory source code exists;
2. clean build passes;
3. full mandatory automated tests pass;
4. stress tests pass;
5. acceptance traceability has no unmapped mandatory IDs;
6. repository created by final build passes `darc verify --level scrub`;
7. a final end-to-end scenario creates multiple snapshots, diffs, restores, corrupts/repairs one chunk, GC's unreachable data, and restores retained snapshots successfully;
8. no open known issue violates a MUST/MUST NOT requirement.

If any item remains incomplete, final reporting MUST explicitly list it as incomplete rather than presenting the project as finished.
