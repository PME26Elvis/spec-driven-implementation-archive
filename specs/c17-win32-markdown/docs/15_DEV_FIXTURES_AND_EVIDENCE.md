# 15 — Deterministic Fixture Generator and Verification/Evidence Manifest Tool

## 1. Workstream Status

This document defines two additional mandatory C17 development utilities for v1.0.

Together with the repository line-count utility, they form Workstream A.

Required utilities:

1. `locscan` — repository inventory/line counting.
2. `fixturegen` — deterministic test workspace/fixture generation.
3. `evidencecheck` — verification/evidence manifest validation.

All three MUST be delivered with source and tests.

## 2. Shared Utility Constraints

Each utility MUST:

- Be implemented in C17.
- Avoid third-party general-purpose parsing/runtime frameworks.
- Have deterministic documented CLI syntax.
- Return documented non-zero exit codes for invalid invocation/failure.
- Write diagnostics to stderr and normal machine-readable output to the selected output file/stdout as documented.
- Avoid depending on the GUI application being open unless the specific operation explicitly validates GUI-produced evidence files.

## 3. `fixturegen` Purpose

`fixturegen` MUST generate deterministic Markdown workspaces used by unit/integration/E2E/performance tests.

The goal is to prevent a submission from relying only on manually authored happy-path examples.

## 4. `fixturegen` CLI

At minimum support:

`fixturegen --profile <name> --output <directory> [--seed <uint64>]`

Required profiles:

- `small`
- `unicode`
- `markdown-all`
- `workspace`
- `medium`
- `large`
- `stress-long-line`
- `failure`

A `--list-profiles` command MUST print available profiles.

Unknown profiles MUST fail with a non-zero exit code.

## 5. Determinism

Given the same utility version, profile, and seed, generated authored fixture file bytes MUST be identical across repeated runs on Windows. Generated manifest-relative paths MUST use `/` separators independent of native path syntax.

Timestamps stored inside fixture content MUST be fixed/deterministic, not current wall-clock time.

Directory enumeration order MUST NOT influence generated bytes.

## 6. PRNG

If randomized variation is used, the submission MUST implement and document a fixed PRNG algorithm whose output is independent of libc `rand()` implementation.

A recommended simple contract is xorshift64* or PCG32, but the exact algorithm MAY differ if documented and regression-tested with golden first-N outputs.

Default seed MUST be a fixed constant.

## 7. `small` Profile

Must generate a compact workspace with at least:

- 3 Markdown files.
- 1 relative image asset.
- 1 Base64-embedded image.
- Headings.
- Paragraphs.
- Lists.
- Link.
- Code block.
- Table.

This profile is intended for fast E2E smoke tests.

## 8. `unicode` Profile

Must generate fixtures containing:

- Traditional Chinese paragraphs.
- English paragraphs.
- Mixed Chinese/English/numbers.
- Accented Latin characters.
- Combining-mark sequences used by cursor/deletion tests.
- Emoji variation selector sequence.
- At least two emoji ZWJ sequences used by cursor/deletion tests.
- Paths containing spaces and Traditional Chinese.
- Search/replace repeated Chinese phrase.

The exact strings generated by the default seed MUST be checked into a golden expectation or encoded in tests.

## 9. `markdown-all` Profile

Must include every required Markdown construct from the Markdown specification, including nested/edge combinations.

It MUST also include intentionally incomplete/malformed Markdown states.

The profile MUST be sufficient to drive parser/render snapshot or structure tests without hand-authoring a separate construct corpus.

## 10. `workspace` Profile

Must generate:

- Nested directories at least 4 levels deep.
- At least 20 Markdown files.
- Duplicate filenames in different directories.
- Relative links among Markdown files.
- Relative images using `./` and `../` forms.
- At least one filename containing spaces.
- At least one Traditional Chinese filename.
- Asset directory.
- A `.mdeditor/` directory only when a particular fixture case explicitly requires metadata; clean workspace generation MUST not pre-seed fake application state.

## 11. `medium`, `large`, and `stress-long-line`

These profiles MUST satisfy the size/content requirements of `14_PERFORMANCE_AND_FAILURE_HANDLING.md`.

Generation itself MUST complete without requiring network access.

Images MAY be generated as small deterministic BMP/PNG assets or copied from authored fixture bytes shipped with the test source.

## 12. `failure` Profile

Must generate or prepare cases for:

- Invalid UTF-8 file.
- Malformed Markdown.
- Missing image reference.
- Corrupt supported image file for PNG, JPEG, and BMP.
- Truncated JSON workspace-state sample.
- Truncated history record sample.
- Truncated recovery record sample.
- Read-only/denied-write file or directory case.
- Locked-target/sharing-violation preparation case.
- Windows-invalid/reserved filename test descriptors.
- Long-path workspace containing Traditional Chinese and an absolute path over 260 UTF-16 code units.
- Directory reparse-point/junction cycle where host policy permits; otherwise data required by the mandatory deterministic production-traversal boundary test.

The fixture generator MUST NOT intentionally fill the real disk to simulate a disk-full condition; disk-full behavior must use the application's fault-injection harness.

## 13. Fixture Manifest

Every generation run MUST create `fixture-manifest.json` at the output root.

The manifest MUST contain:

- Manifest schema version.
- Fixture generator version.
- Profile.
- Seed.
- Ordered file entries.
- Relative path for every generated regular fixture file.
- Byte size.
- SHA-256 digest.
- Logical role/category.

Directory entries MAY also be listed but regular files are mandatory.

## 14. SHA-256

Workstream A MUST include a C17 SHA-256 implementation used by fixture/evidence manifests, unless the implementation uses a narrowly scoped operating-system cryptographic hashing API that is explicitly documented.

Calling an external `sha256sum` process is not acceptable as the implementation of manifest hashing.

The SHA-256 implementation MUST be covered by known-answer unit tests.

## 15. `fixturegen --verify`

The utility MUST support verifying an existing generated fixture directory against its manifest.

At minimum:

`fixturegen --verify <directory>`

Verification MUST fail for:

- Missing listed file.
- Byte-size mismatch.
- Digest mismatch.
- Invalid manifest structure.

Extra unlisted files MAY be reported as warnings or errors; behavior MUST be documented.

## 16. `evidencecheck` Purpose

`evidencecheck` validates that a submission's required acceptance evidence is present, internally consistent, and tied to the tested build/fixtures.

It does NOT determine whether a screenshot looks correct and does NOT replace human visual inspection.

It MUST NOT fabricate passing results.

## 17. Evidence Manifest

The submission MUST produce an evidence manifest named:

`evidence/manifest.json`

The manifest MUST be machine-readable JSON using the schema defined by the task pack.

## 18. Evidence Manifest Top-Level Fields

Required fields:

- `schema_version`
- `product_version`
- `build_id`
- `source_revision` or equivalent source-tree identity when available
- `generated_at`
- `test_summary`
- `test_runs`
- `screenshots`
- `fixtures`
- `performance_runs`
- `failure_runs`
- `artifacts`

`generated_at` MAY use wall-clock time because it describes evidence generation, unlike deterministic fixtures.

## 19. Test Summary

`test_summary` MUST include numeric:

- total
- passed
- failed
- skipped

Release evidence MUST have `failed = 0`.

Mandatory release tests MUST NOT be marked skipped.

## 20. Test Run Entries

Each test-run entry MUST contain:

- Stable test/run identifier.
- Category: unit/integration/e2e/performance/failure/regression.
- Result.
- Start/end or duration.
- Path to machine-readable or text log.
- SHA-256 of referenced log.

A single aggregate runner log MAY serve multiple test IDs only if the mapping is explicit.

## 21. Screenshot Entries

Each screenshot entry MUST contain:

- Stable screenshot ID from the acceptance specification.
- Relative path.
- SHA-256.
- Width.
- Height.
- Short state description.
- Related acceptance requirement IDs.

The tool MUST verify file existence, digest, and that the file is a parseable supported image header sufficient to determine width/height.

It need not perform semantic image recognition.

## 22. Required Screenshot Set

At minimum the manifest MUST include IDs for:

- `UI-EMPTY-LIGHT`
- `UI-EMPTY-DARK`
- `UI-WORKSPACE-MULTITAB`
- `UI-SOURCE`
- `UI-SPLIT`
- `UI-PREVIEW`
- `UI-RENDERED-EDIT`
- `UI-MARKDOWN-ALL`
- `UI-IMAGE-SELECTED`
- `UI-IMAGE-RESIZE`
- `UI-TABLE-EDIT`
- `UI-OUTLINE`
- `UI-COMMAND-PALETTE`
- `UI-STATISTICS`
- `UI-VERSION-HISTORY`
- `UI-DIFF-SIDE-BY-SIDE`
- `UI-DIFF-INLINE`
- `UI-MODAL-BLUR`
- `UI-FROSTED-SCROLLED`
- `UI-EXTERNAL-CONFLICT`
- `UI-RECOVERY-CENTER`
- `UI-ERROR-SAVE`
- `UI-DPI-SCALED`

Animation states MAY require more screenshots or a captured sequence as defined in the UI acceptance document.

## 23. Fixture References

The evidence manifest MUST reference the exact fixture manifests used for mandatory E2E/performance runs.

`evidencecheck` MUST verify their SHA-256 digests.

This prevents a performance result from claiming one fixture while executing a materially smaller one.

## 24. Performance Entries

Each performance entry MUST include:

- Fixture profile and manifest digest.
- Operation.
- Number of runs.
- Measured durations or summary statistics required by the performance test.
- Pass/fail against the applicable gate.
- Environment summary sufficient for human context: OS, architecture, CPU logical count, and memory total.

Environment summary is evidence metadata, not a prescribed development environment.

## 25. Failure-Test Entries

Each mandatory fault case MUST have a stable identifier and result.

Entries MUST identify the injected fault or corrupt fixture and the verification performed, such as original-file digest unchanged.

## 26. Artifact Entries

The evidence manifest MUST list at least:

- Application executable/build artifact.
- `locscan`.
- `fixturegen`.
- `evidencecheck`.
- Test executable(s)/runner entry points as applicable.
- Main LOC report.

For each list path, byte size and SHA-256 are mandatory.

## 27. `evidencecheck` Validation

The tool MUST validate:

- JSON syntax/schema subset.
- Required top-level fields.
- Required screenshot IDs.
- Required test categories.
- Zero failed mandatory tests.
- No skipped mandatory release-gate tests.
- Referenced path remains inside evidence/submission root after normalization.
- Referenced file exists.
- Recorded byte size matches when present.
- SHA-256 matches.
- Fixture manifests verify.
- Performance/failure required IDs are present.

## 28. Path Security

Manifest paths MUST be relative.

`evidencecheck` MUST reject paths that escape the selected root through `..`, absolute paths, or equivalent normalization tricks.

Windows reparse-point handling MUST not allow evidence references to silently escape the root; default is reject external targets. Drive-letter absolute paths, UNC paths, extended-namespace absolute paths, rooted backslash paths, and `..` escapes are invalid evidence references as frozen by `16_WINDOWS_PLATFORM_CONTRACT.md`.

## 29. Exit Codes

The following Workstream A exit-code convention is mandatory:

- `0`: success / validation passed.
- `2`: command-line usage error.
- `3`: configuration/manifest parse or schema error.
- `4`: input filesystem/read error.
- `5`: output filesystem/write error.
- `6`: verification mismatch or required evidence missing.
- `7`: internal consistency error.

Utilities MAY define additional codes >= 8 if documented.

## 30. Human-Readable Summary

Both `fixturegen --verify` and `evidencecheck` MUST print a concise human-readable summary including pass/fail and counts.

Machine-readable evidence files remain the authoritative detailed record.

## 31. Self Tests

Workstream A tests MUST include:

- JSON parser valid/invalid cases.
- YAML subset valid/invalid cases used by `locscan`.
- Wildcard/path matching.
- Directory reparse-point/junction traversal-boundary handling.
- SHA-256 known-answer vectors.
- Deterministic PRNG golden output if PRNG used.
- Repeated same-seed fixture byte equality.
- Fixture tamper detection.
- Evidence missing-file detection.
- Evidence digest mismatch detection.
- `../` evidence path escape rejection.
- Required screenshot-ID omission rejection.
- Failed-test count rejection.

## 32. No Circular Trust

The release is not considered verified merely because `evidencecheck` says `PASS`.

Human acceptance MUST still inspect required screenshots and review test/evidence outputs.

The tool's purpose is completeness/integrity checking, not semantic approval.

## 33. Windows Utility Boundary

All three utilities MUST process Unicode Windows root/config/output paths without depending on the current ANSI or console code page.

They MUST support the mandatory long-path fixture and MUST emit UTF-8 JSON with `/`-normalized manifest-relative paths.

`locscan` recursive traversal MUST not follow directory reparse points by default.

`fixturegen` MUST be capable of producing the Windows-specific path/name/failure descriptors required by the Windows platform contract without using a shell command as the implementation of ordinary fixture filesystem operations.

`evidencecheck` MUST reject drive-letter absolute, UNC, extended-namespace, rooted-backslash, `..`, and reparse-point root-escape references.
