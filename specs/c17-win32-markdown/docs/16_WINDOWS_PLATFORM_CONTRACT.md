# 16 — Windows Platform Contract

## 1. Purpose

This document freezes Windows-specific semantics for the v1.0 Windows edition of the task pack.

It does not prescribe an agent, IDE, compiler vendor, package-install procedure, test runner, screenshot tool, or implementation workflow.

It defines only observable product/engineering behavior that differs materially from the Linux/X11 edition or would otherwise be ambiguous on Windows.

## 2. Acceptance Platform

The normative acceptance platform is:

- 64-bit Windows 11 desktop.
- Ordinary interactive desktop session.
- Local NTFS workspace for mandatory filesystem/path/failure tests unless a test explicitly says otherwise.
- At least one installed Traditional Chinese IME for the mandatory IME acceptance flow.
- DPI scale factors capable of exercising 100%, 150%, and 200% behavior, whether through one or multiple displays.

The application MAY support additional Windows versions and filesystems.

UNC/network shares, removable media, FAT-family filesystems, Windows on ARM, and Windows Server are not mandatory v1.0 acceptance targets.

## 3. Unicode Boundary

Markdown document bytes are UTF-8.

Windows-native path strings, shell strings, clipboard text, IME text, and native-dialog results MUST use Unicode-capable Windows APIs.

The application MUST NOT use an ANSI `A`-suffixed Win32 API in a way that causes mandatory Unicode paths/text to depend on the active ANSI code page.

Where the operating-system interface supplies UTF-16, the implementation MAY convert to/from internal UTF-8. Conversion failures MUST be surfaced without data loss.

Unpaired UTF-16 surrogate code units received from a malformed external boundary MUST NOT be converted into invalid UTF-8 and silently persisted.

## 4. Windows Path Model

The application MUST support ordinary absolute local paths such as `C:\Work\Notes\file.md` and relative paths used inside Markdown documents.

Internally equivalent path spellings MUST not create duplicate editable buffers on the normative case-insensitive NTFS acceptance volume.

At minimum path identity logic MUST account for:

- `.` and `..` normalization where resolution is unambiguous.
- Slash vs backslash differences at the Windows filesystem API boundary.
- Drive-letter case.
- Ordinary case-insensitive filename equivalence on the acceptance volume.
- Redundant separators where the Windows API treats them equivalently.

The original/presentable casing SHOULD be retained for UI display.

Markdown link/image destinations generated by the editor MUST continue to use `/` as the Markdown path separator even though native Windows filesystem calls normally use `\`.

## 5. Long Paths

The editor and all three Workstream A utilities MUST support Unicode paths that exceed the legacy 260-character `MAX_PATH` limit for ordinary local-file operations on the normative acceptance filesystem.

The submission MAY use a long-path-aware manifest, extended-length path syntax, or another correct Unicode Win32 approach.

Acceptance MUST include at least one generated nested path whose absolute UTF-16 path length exceeds 260 code units and which contains a Traditional Chinese path component.

The implementation MUST NOT truncate a path for filesystem use merely to make it fit `MAX_PATH`.

Display abbreviations are allowed only in the UI and MUST preserve the full underlying path.

## 6. Windows Filename Rules

The fixture generator and in-application New/Rename UI MUST account for Windows-invalid names.

At minimum, the application MUST reject or fail non-destructively for:

- Names containing `<>:"/\\|?*` where prohibited by Win32 filename rules.
- Empty filename components.
- Components ending in a space or dot when the normal Windows namespace would make the result ambiguous/invalid.
- Reserved DOS device basenames such as `CON`, `PRN`, `AUX`, `NUL`, `COM1`, and `LPT1`, including ordinary extension forms where Windows treats the basename as reserved.

The user-facing error MUST identify that the requested filename is invalid rather than merely reporting an unrelated editor failure.

The mandatory special-character fixture set MUST include spaces, Traditional Chinese, parentheses, square brackets, `#`, `&`, hyphen, and underscore, all of which are legal in ordinary Windows filenames.

## 7. Case Semantics

The normative acceptance workspace uses ordinary case-insensitive NTFS behavior.

Opening `Notes.md` and an equivalent path spelling such as `notes.md` MUST resolve to one document/tab when the filesystem identifies them as the same file.

The application is not required to support Windows per-directory case-sensitive mode as a separate v1.0 behavior.

Search inside Markdown text remains governed by the editor search rules and is independent from filesystem path case semantics.

## 8. Reparse Points, Junctions, and Links

Workspace-tree recursion and Workstream A recursive traversal MUST NOT follow directory reparse points by default.

This includes directory junctions and symbolic-link-style reparse points.

A directory reparse point MAY be displayed as an entry, but default recursive traversal MUST treat it as a leaf/boundary unless an explicit utility option permits following it.

Traversal MUST never loop indefinitely when reparse points form a cycle.

Traversal that would escape the selected workspace/submission/evidence root through a reparse point MUST be rejected by default for security-sensitive evidence validation.

The Windows `locscan` configuration key is `follow_directory_reparse_points`, boolean, default `false`.

A real reparse-point cycle acceptance test SHOULD be used when the test host permits its creation. If host policy prevents creating one, mandatory coverage MUST instead use a deterministic filesystem-boundary test that proves the production traversal code classifies/rejects directory reparse points before recursive descent; the gate may not simply be skipped.

## 9. Workspace Metadata

Workspace-specific state remains stored beneath the selected workspace in `.mdeditor/` exactly as defined by the workspace specification.

That directory MUST remain hidden from the normal workspace tree by application policy even if it does not carry the Windows Hidden attribute.

The implementation MAY additionally set the Hidden attribute, but the product MUST NOT rely on the attribute as the only reason the directory is excluded from ordinary editor navigation.

## 10. Global Preferences and Recents

Global preferences and recent-item state MUST be stored in a per-user Windows application-data location, not beside the executable and not in the current working directory.

The canonical v1.0 logical root is the user's Roaming AppData known folder under an application-owned directory, for example:

`<RoamingAppData>\C17MarkdownEditor\`

The exact product directory spelling MAY differ if documented consistently.

Preferences/recents MUST NOT require administrator privileges.

A portable/no-install mode is optional and MUST NOT replace the mandatory normal per-user behavior in the acceptance build.

## 11. Recovery and Volatile State

Standalone/untitled crash-recovery data and other non-roaming machine-local state MUST be stored under the user's Local AppData known folder in an application-owned directory, for example:

`<LocalAppData>\C17MarkdownEditor\Recovery\`

Workspace-associated recovery MAY remain under `.mdeditor/` when the workspace contract specifies that location.

Recovery MUST NOT be written to the installation directory.

Recovery MUST NOT rely solely on `%TEMP%`, because cleanup of temporary directories must not silently erase the only crash-recovery copy before the application can offer Recovery Center behavior.

## 12. Native File/Folder Dialogs

The application MAY use the Windows Common Item Dialog or an equivalent native Windows Unicode file/folder picker for:

- Open File.
- Save As.
- Open Workspace / Select Folder.
- Insert Image.
- Locate/Relink Image.
- Save Image As.
- Export destination selection.

These native pickers are exempt from the authored modal-animation/blur requirement.

All application-owned confirmation, conflict, statistics, preferences, history, diff, recovery-center, and error surfaces remain subject to the custom UI requirements.

## 13. Clipboard Contract

Plain-text Windows clipboard interoperability is mandatory through the Unicode clipboard format (`CF_UNICODETEXT`) or an exactly interoperable Windows Unicode mechanism.

Copy MUST make the selected text pasteable as Unicode text into an ordinary external Windows application.

Paste MUST accept Unicode text copied from an ordinary external Windows application.

The editor's internal newline model remains LF. When publishing or receiving Windows clipboard text, CRLF ↔ LF normalization MAY occur at the OS boundary, but copying text from the editor and pasting it back into the editor MUST recover the same logical line breaks.

Cut MUST NOT delete source text if the application cannot successfully make the clipboard data available.

Clipboard ownership/allocation failures MUST be non-destructive.

Raw bitmap/DIB clipboard image import remains optional.

## 14. Explorer/File Drag and Drop

The main application window MUST interoperate with ordinary Windows Explorer file dragging.

At minimum:

- Dropping one supported image file on an editable document invokes normal image insertion.
- Dropping multiple image files inserts in deterministic received-list order.
- Dropping a Markdown/text file on the tab/workspace region opens/offers it as a document rather than inserting its path text.
- Unsupported drops produce a non-destructive response.

`WM_DROPFILES`, OLE `IDropTarget`, or another native mechanism MAY be used; the mechanism is not part of acceptance.

Internal selected-text dragging remains application-authored and MUST NOT be delegated to a Rich Edit control.

## 15. IME Composition Contract

Traditional Chinese IME input is mandatory in Source Mode and Rendered Editing Mode.

The application MUST handle the standard Windows composition lifecycle, including start, updates, commit/result text, and cancellation.

During composition:

- Composition text MUST be visually identifiable at/near the caret.
- Intermediate composition MUST NOT become permanent Markdown source until committed.
- Cursor/selection operations MUST NOT split UTF-16 surrogate pairs or corrupt the internal UTF-8 buffer.
- Cancellation MUST remove the transient composition without leaving phantom source bytes.
- A committed composition MUST enter Undo history as one user-meaningful text-insertion transaction.

The implementation MUST position the IME composition/candidate UI reasonably near the custom editor caret using the standard Windows IME integration available to custom-drawn applications.

Acceptance MUST include Traditional Chinese composition and commit using an installed Windows IME, not merely programmatic insertion of Chinese UTF-8 bytes.

## 16. External File Change Detection

Open saved files MUST participate in the same external-change/conflict model as the Linux edition.

On Windows the implementation MAY use `ReadDirectoryChangesW`, periodic metadata/content checks, or another mechanism.

The editor MUST tolerate duplicate/coalesced filesystem notifications and MUST confirm material content/identity changes before presenting destructive choices.

A notification alone is not proof that bytes changed.

The editor SHOULD avoid holding an open document handle in a sharing mode that unnecessarily prevents another ordinary process from writing, renaming, or deleting the document. Acceptance may use a companion process to exercise these operations.

## 17. Safe Save and Replace

A normal Save MUST protect the last successfully saved file from partial-write corruption.

The Windows commit model MUST be equivalent to:

1. Serialize the complete current UTF-8 document to a temporary file in the same target directory.
2. Detect and report short/partial writes.
3. Flush the temporary file's written data using an appropriate Windows durable-flush operation.
4. Close/finish the temporary writer before replacement.
5. Commit by replacing the existing target using a same-volume Windows replace/rename primitive that does not expose a half-written target; when creating a new file, use a correspondingly safe final move/rename.
6. Clear dirty state only after the commit succeeds.
7. Leave the previous target intact when a pre-commit staging/write/flush failure occurs.

`ReplaceFileW` and `MoveFileExW` with appropriate flags are examples of native primitives capable of participating in such a design; these exact functions are not mandatory if observable guarantees are met.

If the target is currently locked by another process and Windows returns a sharing/access error, Save MUST fail visibly and leave the document dirty/in memory. The application MUST NOT discard the edited buffer.

Temporary leftovers from a failed commit MUST be cleaned up when safe or explicitly identified for recovery/diagnosis.

## 18. Read-Only and Access Control

The editor MUST distinguish a file that can be read but cannot be replaced/written from an ordinary successful Save.

Windows Read-only attribute, ACL access denial, sharing violations, and other write failures MAY produce different native error codes but MUST converge on the required non-destructive editor behavior.

The application MUST NOT attempt to bypass filesystem ACLs, elevate privileges, or silently clear a read-only attribute merely to force Save.

Save As to a writable destination remains an available recovery action.

## 19. File Identity and Rename/Delete

The editor MUST update open-tab identity correctly after successful rename operations initiated inside the workspace tree.

External rename/delete behavior MUST satisfy the conflict specification.

Where Windows file identity can be resolved through an opened handle, implementations SHOULD use a stable identity signal to reduce duplicate-tab/conflict ambiguity; however the exact mechanism is not prescribed.

The application MUST not assume POSIX semantics in which an already-open path can always be deleted/renamed independently of sharing flags.

## 20. DPI and Scaling Acceptance

Mandatory visual acceptance includes:

- Main window at 100% scaling.
- Main window at 150% or 200% scaling.
- Custom controls remain correctly hit-testable.
- Text caret and selection remain aligned to glyphs.
- Ripple/glow/blur radii scale consistently.
- Window resize constraints use logical dimensions rather than hard-coded unscaled device pixels.
- Moving the application between different-DPI monitors, where available, does not require restart and does not leave a permanently blurred/incorrectly sized framebuffer.

Screenshot capture method remains unspecified.

## 21. Timing

Animation and responsiveness measurement MUST use a monotonic/high-resolution time source suitable for sub-frame interval measurement.

`QueryPerformanceCounter`/`QueryPerformanceFrequency` are permitted native facilities.

Wall-clock time changes MUST NOT cause an animation timeline to jump backward/forward or invalidate performance measurements.

## 22. External Link Activation

HTTP/HTTPS links activated under the link policy MAY be handed to the user's registered Windows handler.

The editor MUST not embed WebView2/CEF/browser UI to satisfy this behavior.

Malformed or unsupported schemes MUST not be passed blindly to a shell command constructed from document text.

## 23. Evidence Path Rules on Windows

Machine-readable evidence/fixture manifests MUST use root-relative paths with `/` separators for deterministic portability.

`evidencecheck` MUST reject at least:

- Drive-letter absolute paths such as `C:\...` or `C:/...`.
- UNC paths such as `\\server\share\...`.
- Extended namespace absolute paths such as `\\?\...`.
- Rooted backslash paths.
- `..` traversal that escapes the selected evidence/submission root.
- A reparse-point traversal that resolves outside the selected root under the default policy.

Path validation MUST occur before trusting a referenced digest or artifact as part of the submission.

## 24. Workstream A Unicode CLI Behavior

`locscan`, `fixturegen`, and `evidencecheck` MUST accept paths containing Traditional Chinese characters on Windows without depending on the current console code page.

The implementation MAY obtain Unicode command-line arguments through a Windows-specific Unicode entry/boundary mechanism while all utility logic remains authored C17.

Machine-readable JSON output MUST be UTF-8.

Diagnostics SHOULD be usable in a Unicode-capable terminal, but terminal rendering limitations do not excuse incorrect path/file processing.

## 25. Platform-Equivalent Scope Rule

A Windows system component may replace a Linux system integration only when it occupies the same narrow role.

Examples of acceptable parity:

- Win32 window/message/input integration instead of X11 window/event integration.
- WIC system image codec instead of narrowly allowed Linux system image codecs.
- Windows IME integration instead of X11 input-method integration.
- `CF_UNICODETEXT` clipboard instead of X11 UTF-8 clipboard selection.
- Windows per-user AppData instead of XDG user directories.
- Windows file-change notification instead of Linux file-change notification.

Examples of unacceptable scope reduction:

- Rich Edit replacing the authored text editor.
- TreeView replacing the authored workspace tree.
- native tab controls replacing the authored tab strip.
- WebView2 replacing the authored Markdown renderer.
- WinUI/WPF/Windows Forms replacing the authored UI engine.
- a system diff/VCS utility replacing the authored diff/history engine.

The Windows edition MUST remain comparable in functional and implementation difficulty to the corresponding Linux v1.0 assignment.
