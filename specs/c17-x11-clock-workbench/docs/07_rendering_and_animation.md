# 07 — Software Rendering and Animation Requirements

## 1. Software framebuffer

Project B must render mandatory UI into an application-owned pixel buffer.

A recommended pixel format is 32-bit premultiplied or straight-alpha RGBA/BGRA, but the implementation must use one clearly documented convention.

Alpha blending must be mathematically consistent with that convention.

## 2. Mandatory drawing primitives

The hand-built renderer must provide sufficient primitives to draw all required UI.

At minimum:

- clear/fill;
- rectangle fill;
- rounded rectangle fill;
- rounded rectangle border;
- circle/ellipse fill;
- line segment with configurable width;
- anti-aliased line or acceptable supersampled equivalent;
- arc/circular tick geometry;
- glyph/text blit/render;
- image/buffer compositing;
- alpha blending;
- clipping rectangle;
- drop shadow approximation;
- blur operation.

## 3. Anti-aliasing

Clock face, hands, circles, rounded corners, and diagonal geometry must not appear as raw one-pixel stair-step primitives at normal sizes.

Acceptable approaches include:

- coverage-based rasterization;
- analytical distance functions;
- supersampling with downsampling;
- other custom software techniques.

Using a forbidden graphics library is not acceptable.

## 4. Rounded rectangles

Rounded rectangles must support radius clamping when width/height are too small.

They must not read/write outside framebuffer bounds when partially clipped.

## 5. Line joins/caps

Clock hands should use visually appropriate caps and center attachment.

The exact geometry may be polygonal rather than a generic line primitive if desired.

## 6. Alpha compositing

Layered components must composite correctly.

At minimum test semi-transparent overlay over known background values.

Repeated animation frames must redraw from a coherent base rather than accumulating alpha indefinitely.

## 7. Shadows

Button/card/nav/modal shadows must be generated by the application.

A shadow can be implemented using blurred masks, layered translucent shapes, or another spatial approximation.

A single hard offset rectangle is insufficient for the primary modern elevation effects.

## 8. Blur

The renderer must implement a blur suitable for:

- modal background blur;
- dynamic frosted navigation;
- glow/shadow masks if reused.

A separable box blur, repeated box blur approximating Gaussian, or separable Gaussian kernel is acceptable.

## 9. Blur radius

Configuration must allow a visible range of blur strengths.

The renderer must handle radius zero as a fast no-op/copy path. Required modal/nav transitions expose a fractional effective blur strength between integer configured endpoints. If the underlying kernel accepts only integer radii, the implementation must blend/interpolate appropriate blurred results so the visible transition remains continuous rather than stepping once per integer radius.

Very large configured radii must be bounded by schema validation to avoid pathological work.

## 10. Blur boundaries

Blur sampling near edges must use a deterministic boundary policy, such as clamp-to-edge.

The implementation must not read outside allocated memory.

## 11. Offscreen layers

The application may use temporary/offscreen buffers for:

- pre-navigation scene;
- modal background;
- blur intermediate passes;
- shadow masks;
- transition compositing.

Allocation should be reused across frames where practical.

## 12. Allocation discipline

The normal animation loop must not allocate and free large full-window buffers unnecessarily every frame.

Framebuffer-sized working storage should be retained/reused and resized only when needed.

## 13. Resize handling

On window resize:

- framebuffer dimensions update safely;
- old buffers are released only after replacement allocation succeeds or a safe fallback is chosen;
- layout recomputes;
- next frame fully redraws;
- no stale-stride assumptions remain.

## 14. Allocation failure

If framebuffer reallocation fails, the application must fail safely.

It may retain the previous buffer/size temporarily and show an error if possible, or exit with diagnostics if continued rendering is impossible.

Memory corruption is never acceptable.

## 15. Frame timing

Animation progression uses monotonic elapsed time, not frame count.

Running at 30 FPS versus 144 FPS must produce approximately the same transition duration.

## 16. Animation clock

UI animations use a separate conceptual progression from simulated clock time.

Changing playback rate must not speed up or reverse UI hover/modal animations.

## 17. Animation representation

Each active animation needs at least:

- start state/value;
- target state/value;
- start time;
- duration;
- easing function;
- completion semantics.

For every interruptible animation, retargeting uses this fixed rule: evaluate the current interpolated visual value at the retarget timestamp, use that value as the new start value, use the newly requested state as target, set start time to the retarget timestamp, and use the normal configured duration multiplied by `1 / animation.speed_multiplier`. No queued stale endpoint may execute afterward.

## 18. Required animated transitions

When animations are enabled, the following must animate smoothly:

- button hover elevation/glow;
- button ripple;
- capsule navigation movement;
- toggle switch movement;
- modal open/close scale and opacity;
- modal background dim/blur;
- Settings nav collapse;
- Settings nav frosted blur/shadow strength;
- page/view transition;
- top-level application scene entrance/normal-exit transition;
- slider thumb hover/pressed emphasis.


## 18A. Top-level application scene entrance/exit

The X11 top-level window itself is not required to use compositor opacity APIs. Instead, the application must animate its complete rendered scene inside the window.

On an ordinary successful launch with animations enabled:

- the first mapped scene starts at opacity 0 and visual scale 0.97 centered in the content area;
- it transitions to opacity 1 and scale 1 using the same custom easing infrastructure;
- default duration is `modal_open_ms`;
- mandatory page controls are not activated until the entrance completes.

On a normal user-requested close after all Save/Discard/Cancel decisions are resolved:

- the current scene transitions from opacity 1/scale 1 toward opacity 0/scale 0.97;
- default duration is `modal_close_ms`;
- new state-mutating input is blocked during exit;
- dirty-configuration resolution and required runtime-state persistence (including any retry/exit-without-saving decision) occur **before** this exit animation begins;
- after the transition reaches its endpoint, the X11 window is destroyed without another hidden persistence attempt.

Fatal startup errors that occur before a usable UI exists and forced process termination are exempt. When animations are disabled, entrance/exit reaches the final state immediately.

## 19. Recommended durations

Default duration targets:

- hover elevation: 100–180 ms;
- press feedback: 70–140 ms;
- ripple: 300–550 ms;
- capsule slide: 180–320 ms;
- toggle: 140–240 ms;
- modal open: 220–360 ms;
- modal close: 160–280 ms;
- page transition: 180–320 ms.

Actual defaults are configuration values subject to ranges.

## 20. Cubic Bézier evaluator

At least one reusable cubic Bézier easing implementation is required.

It must map normalized animation progress to eased progress.

If arbitrary x control points are supported, the implementation must correctly solve/invert the x dimension rather than assuming parameter `t == x` unless control points are constrained so that this is valid.

For the fixed curves required by the visual specification, the implementation must solve the x dimension to obtain y at a requested normalized time progress. A generic reusable evaluator may support additional curves, but replacing the required curve with `t == parameter` when x control points are nontrivial is not compliant.

## 21. Easing stability

Easing evaluator must handle progress below 0 and above 1 by clamping to endpoint behavior.

It must not generate NaN for valid configured control points.

## 22. Ripple implementation

Each button may maintain a small bounded list of active ripples.

Rapid clicks must not cause unbounded allocation growth.

Old completed ripples must be removed/reused.

## 23. Hover interruption

Moving the pointer rapidly in/out of a button must smoothly reverse or retarget hover animation from the current visual state.

It must not restart from zero each time and visibly pop.

## 24. Modal interruption

If a modal is closed while opening, its close transition must continue from the current interpolated scale/opacity/blur state. Opening again while closing must likewise retarget from the current interpolated state without jumping to an old endpoint.

## 25. Page transitions and input

During a Clock/Settings page transition:

- all page-content controls on both old and new pages are non-interactive for the duration of the transition;
- the top navigation itself remains able to retarget/reverse the transition;
- old page must not receive clicks once transition begins;
- focus moves to the first appropriate control on the target page only after transition completes.

Rapidly switching the capsule while a page transition is active must retarget from the current interpolated visual state rather than queueing stale transitions.

## 26. Frosted navigation algorithm

A compliant implementation must:

1. render Settings content beneath the nav to an offscreen/base buffer;
2. determine nav effect progress from scroll offset;
3. sample/copy the nav-underlay region;
4. apply blur with strength derived from effect progress;
5. composite translucent nav tint;
6. render nav controls sharply on top;
7. add bottom shadow based on effect progress.

Equivalent custom approaches are allowed if the visual/result semantics are the same.

## 27. Scroll interpolation

Frosted/collapse progress uses the configured range exactly:

```text
p = clamp(scroll_y / effects.frost_scroll_range, 0, 1)
```

The blur, tint, shadow, and collapse transforms may each apply different easing to `p`, but all must be continuous.

## 28. Settings scrolling

Settings content must use application-managed scroll state.

Requirements:

- mouse wheel scroll;
- clipping to viewport;
- bounds clamping;
- no blank overscroll beyond reasonable optional elastic effect;
- nav remains visually anchored while content scrolls underneath.

## 29. Scrollbar

A visible scrollbar is optional if content position remains discoverable, but if implemented it must be custom-rendered and draggable.

## 30. Performance expectation

At the reference size near `1100×760`, ordinary smooth clock playback and hover animations should remain visually interactive on a typical contemporary desktop CPU.

No exact FPS is a release gate, but persistent multi-second input lag or obviously unusable frame rates are defects.

## 31. Dirty rendering

Full-window redraw is allowed.

Dirty-region rendering is optional.

Correctness and artifact-free output take precedence.

## 32. Deterministic renderer tests

Renderer unit tests must cover primitive edge cases without requiring visual inspection only.

Examples:

- clipping writes only within region;
- alpha blend expected pixel values within tolerance;
- zero-radius blur preserves input;
- blur of impulse produces symmetric result for symmetric kernel;
- rounded rectangle does not write out of bounds;
- line hit-test geometry matches visual geometry sufficiently.

## 33. Screenshot/reference validation

The test suite may render deterministic frames to a simple lossless format implemented by the project, such as PPM, for human inspection.

A screenshot file is validation evidence only; pre-rendered screenshots must not be used as the actual application UI.
