# C17 / X11 Embedded Database Workbench — Software Implementation Task Specification

**Specification version:** 1.0.0
**Status:** Version 1.0 — complete implementation and acceptance specification
**Normative keywords:** MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY

This document defines the complete required product, engineering behavior, file formats, command behavior, GUI behavior, validation obligations, error handling, edge cases, tests, evidence, and Definition of Done for a self-contained embedded database engine and desktop database workbench.

Unless a requirement is explicitly marked OPTIONAL, it is mandatory.

## 1. Product Summary

The deliverable is a native Linux desktop application and command-line database system written in C17. The central product is a self-contained embedded relational database engine implemented from first principles. The same engine SHALL be used by both the CLI and the X11 desktop workbench.

The project SHALL demonstrate real persistence, single-column and composite B+ tree indexing, query execution, snapshot-isolation MVCC, transactions, durability, recovery, corruption detection, authenticated encryption, maintenance operations, import/export, Unicode-safe text handling, and a modern custom-rendered desktop user interface.

- **P-001** — The database engine is the product core. The GUI and CLI are front ends over the same engine implementation; duplicated or divergent storage engines are forbidden.
- **P-002** — The application SHALL open existing database files and create new database files using the format defined by this project.
- **P-003** — The implementation SHALL be usable without any network service, remote API, external database server, or runtime-generated remote dependency.
- **P-004** — All persistence SHALL be local-file based.
- **P-005** — All required features SHALL be real and wired to persistent state. Demonstration-only behavior, fake rows, hard-coded query results, placeholder controls, or no-op commands are forbidden.
## 2. Language, Platform, and Dependency Boundary

- **ENG-001** — All production source code SHALL be ISO C17.
- **ENG-002** — C++ is forbidden in production code.
- **ENG-003** — Third-party GUI frameworks and widget toolkits are forbidden, including GTK, Qt, SDL, GLFW, wxWidgets, FLTK, Electron, and browser-based UI shells.
- **ENG-004** — X11/Xlib and X11 protocol support libraries MAY be used only as the native window-system boundary for window creation, event input, clipboard/selection integration, cursor control, and presentation of pixels.
- **ENG-005** — All application widgets, controls, layouts, text editing behavior, data grids, menus, dialogs, scrolling, animation, shadows, blur, glow, and transitions SHALL be implemented by the submission.
- **ENG-006** — Third-party database, SQL, parser, storage-engine, indexing, transaction, WAL, cryptography, compression, serialization, or data-structure libraries are forbidden.
- **ENG-007** — SQLite, Berkeley DB, LMDB, RocksDB, LevelDB, DuckDB, PostgreSQL client/server substitution, or invoking their command-line tools is forbidden.
- **ENG-008** — System/POSIX facilities MAY be used for file descriptors, locking, durability barriers, clocks, secure randomness, process control needed by tests, and memory mapping. These facilities SHALL NOT replace required database algorithms.
- **ENG-009** — The build SHALL be driven by a Makefile and SHALL produce all required executables from source.
- **ENG-010** — Generated parser generators or code generators are forbidden. The SQL lexer and parser SHALL be authored as project source.
- **ENG-011** — The product SHALL not require a network connection to build, test, launch, or operate after the required system interfaces are present.
- **ENG-012** — Undefined behavior, signed-integer overflow reliance, unaligned aliasing tricks without guarded portable fallbacks, or host-endian on-disk serialization are forbidden.

## 4. Executables and Roles

- **BIN-001** — `edb` SHALL be the command-line database shell and batch executor.
- **BIN-002** — `edb-gui` SHALL be the native X11 desktop workbench.
- **BIN-003** — `edb-check` SHALL validate database structural integrity without modifying the database unless an explicit repair option is supplied.
- **BIN-004** — `edb-fixture` SHALL generate deterministic fixture databases and data files for tests.
- **BIN-005** — `edb-crashrun` SHALL execute crash-injection durability scenarios against a child database process.
- **BIN-006** — `locscan` SHALL count authored source/document/test/config lines according to a config file and ignore rules.
- **BIN-007** — All executables SHALL support `--help` and return a nonzero status for invalid invocation.
## 5. Repository Layout Requirements

The exact filenames MAY differ, but the logical separation below SHALL be recognizable:

```text
src/              production implementation
include/          public or shared headers
tests/            unit/integration/crash/corruption/GUI tests
fixtures/         deterministic source fixtures or fixture definitions
tools/            required developer utilities
docs/             human-readable engineering documentation
Makefile          top-level build entry point
README.md         build/use/limits/recovery documentation
```

- **TREE-001** — Production source SHALL NOT depend on files generated by running tests.
- **TREE-002** — Tests MAY generate disposable files under a dedicated temporary test directory.
- **TREE-003** — Temporary artifacts SHALL be removable through `make clean`.
## 6. Database File Model

- **FMT-001** — The engine SHALL use a documented binary page-oriented file format.
- **FMT-002** — Logical database pages SHALL have a fixed size of 4096 bytes unless this document specifies an envelope around a logical page.
- **FMT-003** — The file header SHALL contain a magic identifier, file-format major/minor version, page size, feature flags, cryptographic metadata, database identifier, and integrity metadata.
- **FMT-004** — All multibyte numeric fields on disk SHALL use one explicitly documented byte order independent of host endianness.
- **FMT-005** — Every page SHALL have a type identifier, page number, generation or change counter, payload bounds, and integrity information sufficient to detect damage.
- **FMT-006** — Page zero SHALL be reserved for file-level metadata and SHALL NOT be used as a user table/index page.
- **FMT-007** — The format SHALL distinguish at minimum metadata/schema pages, B+ tree internal pages, B+ tree leaf pages, overflow pages, freelist pages, and recovery-related metadata.
- **FMT-008** — Unknown incompatible major format versions SHALL be rejected without modification.
- **FMT-009** — Unknown optional feature flags SHALL be rejected unless explicitly marked forward-compatible by the format.
- **FMT-010** — The database SHALL retain enough metadata to distinguish an initialized empty database from a truncated or random file.
- **FMT-011** — The engine SHALL never interpret arbitrary unvalidated bytes as trusted page counts, offsets, lengths, or allocation sizes.
- **FMT-012** — Opening a malformed database SHALL fail safely without unbounded allocation, out-of-bounds access, or overwrite of the original file.
### 6.1 File Header Minimum Fields

- **FMT-H-01** — Header SHALL encode `magic`: fixed signature identifying this database family.
- **FMT-H-02** — Header SHALL encode `format_major`: incompatible format generation.
- **FMT-H-03** — Header SHALL encode `format_minor`: compatible format revision.
- **FMT-H-04** — Header SHALL encode `page_size`: logical page size.
- **FMT-H-05** — Header SHALL encode `database_id`: random identifier for this database.
- **FMT-H-06** — Header SHALL encode `feature_flags`: enabled file features.
- **FMT-H-07** — Header SHALL encode `kdf_id`: password KDF identifier.
- **FMT-H-08** — Header SHALL encode `kdf_iterations`: KDF work parameter.
- **FMT-H-09** — Header SHALL encode `salt`: per-database KDF salt.
- **FMT-H-10** — Header SHALL encode `header_generation`: monotonic metadata generation.
- **FMT-H-11** — Header SHALL encode `root_schema_page`: entry page for schema metadata.
- **FMT-H-12** — Header SHALL encode `freelist_root`: entry page or descriptor for free pages.
- **FMT-H-13** — Header SHALL encode `last_page_number`: highest allocated logical page.
- **FMT-H-14** — Header SHALL encode `checkpoint_sequence`: last durable checkpoint sequence.
- **FMT-H-15** — Header SHALL encode `header_checksum_or_tag`: header integrity/authentication value.
## 7. Pager and Buffer Manager

- **PAGER-001** — All table/index access SHALL go through a pager abstraction rather than arbitrary direct offsets throughout the SQL layer.
- **PAGER-002** — The pager SHALL validate page numbers and file bounds before reading.
- **PAGER-003** — The pager SHALL maintain an in-memory page cache with a documented bounded replacement policy such as clock or LRU.
- **PAGER-004** — Dirty state SHALL be tracked per cached page.
- **PAGER-005** — Pinned/in-use pages SHALL NOT be evicted.
- **PAGER-006** — The pager SHALL distinguish short read, checksum/authentication failure, impossible page type, invalid payload bounds, and generic I/O errors.
- **PAGER-007** — Page creation SHALL not expose partially initialized pages to higher layers.
- **PAGER-008** — Page writes SHALL participate in transaction/WAL ordering rather than bypassing durability rules.
- **PAGER-009** — The cache SHALL have tests that force eviction with a cache smaller than the working set.
- **PAGER-010** — The engine SHALL operate correctly when cache capacity is one page greater than the minimum needed for a tested operation.
- **PAGER-011** — Cache statistics SHALL expose hits, misses, evictions, dirty writes, and pinned-page peak for diagnostics.
- **PAGER-012** — Closing a connection SHALL release all cache resources and file descriptors even following an error.
## 8. Record and Value Representation

- **REC-001** — Supported SQL value classes SHALL include NULL, signed 64-bit INTEGER, IEEE-754 64-bit REAL, UTF-8 TEXT, and arbitrary BLOB.
- **REC-002** — BOOLEAN MAY be accepted syntactically but SHALL have a documented mapping to the core value classes.
- **REC-003** — Rows SHALL use a deterministic self-describing or schema-driven binary serialization that validates all field lengths before access.
- **REC-004** — Variable-length records larger than a leaf-page local payload threshold SHALL use overflow pages rather than requiring a page larger than the fixed page size.
- **REC-005** — Overflow chains SHALL be cycle-checked and bounds-checked during integrity validation.
- **REC-006** — A single TEXT or BLOB value of at least 1 MiB SHALL be supported through overflow storage.
- **REC-007** — A zero-length TEXT and a zero-length BLOB SHALL remain distinguishable from NULL.
- **REC-008** — NaN and infinity behavior for REAL SHALL be documented and tested; they SHALL NOT silently corrupt ordering structures.
- **REC-009** — Row serialization SHALL be endian-stable and deterministic.
- **REC-010** — Malformed record headers SHALL be reported as corruption, not interpreted using unchecked lengths.
## 9. Page Allocation, Free Space, and Compaction

- **ALLOC-001** — The engine SHALL maintain reusable free pages.
- **ALLOC-002** — Deleting rows or dropping tables/indexes SHALL eventually make unreachable pages reclaimable.
- **ALLOC-003** — Freelist metadata SHALL itself be validated for duplicate entries, out-of-range pages, and cycles.
- **ALLOC-004** — Page allocation SHALL prefer reusable pages before indefinitely extending the file where safe.
- **ALLOC-005** — The engine SHALL implement an explicit `VACUUM` or equivalent compaction operation.
- **ALLOC-006** — Compaction SHALL rebuild the database into a consistent compact form and replace the original atomically only after successful completion.
- **ALLOC-007** — An interrupted compaction SHALL leave either the old valid database or the new valid database, not a half-written primary file.
- **ALLOC-008** — Compaction SHALL preserve all logical rows, schema objects, constraints, indexes, and encryption settings.
- **ALLOC-009** — Database size before/after compaction SHALL be available in maintenance statistics.
- **ALLOC-010** — Free-page reuse SHALL be covered by tests that repeatedly insert and delete enough data to span many pages.
## 10. B+ Tree Implementation

Tables and secondary indexes SHALL be backed by project-authored B+ trees. A sorted flat file or linear list is not an acceptable substitute for indexed structures.

- **BTREE-001** — B+ tree internal and leaf nodes SHALL have distinct on-disk representations.
- **BTREE-002** — Tree search SHALL descend by key comparisons and SHALL NOT linearly scan all pages for an indexed equality lookup.
- **BTREE-003** — Leaf pages SHALL store ordered entries.
- **BTREE-004** — Internal pages SHALL store separator keys and child references.
- **BTREE-005** — Insertion SHALL implement leaf splitting.
- **BTREE-006** — Insertion SHALL implement internal-node splitting and root creation.
- **BTREE-007** — Deletion SHALL implement removal from leaf nodes.
- **BTREE-008** — Deletion SHALL implement redistribution/borrowing where applicable.
- **BTREE-009** — Deletion SHALL implement merge/coalescing where applicable.
- **BTREE-010** — Deletion SHALL shrink the root when the previous root becomes redundant.
- **BTREE-011** — Parent separator keys SHALL remain correct after first-key changes in child pages.
- **BTREE-012** — Duplicate-key handling SHALL obey index uniqueness rules.
- **BTREE-013** — Range traversal SHALL return keys in deterministic order.
- **BTREE-014** — Leaf sibling navigation MAY be used and, if present, SHALL be integrity-checked.
- **BTREE-015** — Each B+ tree SHALL expose validation logic checking sort order, occupancy rules, child ranges, page reachability, and cycles.
- **BTREE-016** — Tests SHALL force at least three tree levels, not only root-plus-leaf examples.
- **BTREE-017** — Tests SHALL insert ascending, descending, alternating, and pseudorandom key sequences.
- **BTREE-018** — Tests SHALL delete keys in orders chosen to force borrow-left, borrow-right, merge-left, merge-right, and root collapse cases.
- **BTREE-019** — Variable-length TEXT keys SHALL be supported for secondary indexes within documented maximum key size limits.
- **BTREE-020** — Oversized index keys SHALL fail with a specific error without corrupting the transaction.

### 10.1 Composite B+ Tree Indexes

Composite indexes are mandatory. They SHALL be implemented as true ordered tuple keys inside the project-authored B+ tree. Maintaining several independent single-column indexes and intersecting their results is not an acceptable substitute for a required composite index.

- **CIDX-001** — `CREATE [UNIQUE] INDEX name ON table(col1, col2, ...);` SHALL accept from one through at least four indexed columns.
- **CIDX-002** — The schema catalog SHALL persist the ordered list of indexed columns. Column order is semantically significant.
- **CIDX-003** — Composite index keys SHALL have an unambiguous binary encoding containing sufficient type/null/length information so distinct tuples cannot alias through concatenation ambiguity.
- **CIDX-004** — Composite keys SHALL compare lexicographically: component 1 first; component 2 only when component 1 compares equal; and so on.
- **CIDX-005** — Each component SHALL use the same deterministic type and collation comparison semantics used by SQL predicates for that column.
- **CIDX-006** — NULL ordering inside index keys SHALL be deterministic and SHALL match the documented engine ordering semantics.
- **CIDX-007** — A nonunique composite index SHALL include a deterministic row identity/version discriminator after the logical tuple so multiple equal logical keys can coexist without overwriting one another.
- **CIDX-008** — A UNIQUE composite index SHALL enforce uniqueness over the complete indexed tuple.
- **CIDX-009** — For UNIQUE indexes, any tuple containing one or more NULL components SHALL be treated according to one explicitly documented SQL-consistent rule. Version 1.0 requires the common rule that NULL-containing tuples do not conflict with one another; two fully non-NULL equal tuples SHALL conflict.
- **CIDX-010** — Insert, update, delete, rollback, crash recovery, VACUUM, rekey, salvage, and index rebuild SHALL preserve composite index correctness.
- **CIDX-011** — Updating any indexed component SHALL atomically retire/remove the old logical tuple entry and create the new logical tuple entry according to MVCC visibility rules.
- **CIDX-012** — Updating a non-indexed column SHALL not create a logically different composite key, although MVCC representation MAY require version metadata maintenance.
- **CIDX-013** — The planner SHALL support the leftmost-prefix rule. For index `(a,b,c)`, predicates constraining `a`, `(a,b)`, or `(a,b,c)` MAY use the index; a predicate on `b` or `c` alone SHALL NOT be claimed as a direct ordered lookup on that index.
- **CIDX-014** — The planner SHALL support equality on a leading prefix followed by a bounded range on the next component; e.g. `(a = ? AND b = ? AND c BETWEEN ? AND ?)` for index `(a,b,c)`.
- **CIDX-015** — Once a range condition is used on a composite key component, later components SHALL NOT be claimed as narrowing the ordered seek interval unless the implementation demonstrably supports a correct stronger transformation.
- **CIDX-016** — `ORDER BY` MAY be satisfied by a composite index when ordering is proven compatible with its key order and constrained leading prefix. Otherwise an explicit sort SHALL remain in the plan.
- **CIDX-017** — Index-assisted nested-loop joins SHALL be able to use a composite index when the inner-side join predicates constrain a usable leading prefix.
- **CIDX-018** — `EXPLAIN` SHALL identify the composite index and the number/names of leading key components used for seek/range bounds.
- **CIDX-019** — The planner SHALL NOT report use of a composite index when execution actually performs a complete table scan or complete unrelated-index scan.
- **CIDX-020** — Composite index key-size limits SHALL be based on the serialized complete tuple and SHALL be checked before modifying persistent state.
- **CIDX-021** — If one component causes the serialized composite key to exceed the supported key limit, the statement SHALL fail atomically with a specific key-too-large error.
- **CIDX-022** — Composite index validation SHALL verify tuple ordering, component decode validity, uniqueness rules, row references, MVCC visibility metadata where present, and B+ tree structural invariants.
- **CIDX-023** — Index rebuild SHALL reconstruct composite tuple keys from table rows/versions rather than copying possibly corrupted source index bytes.
- **CIDX-024** — `ANALYZE` SHALL collect at minimum total entry count and distinct-count estimates for the first indexed component; it SHOULD collect distinct-prefix estimates for `(c1,c2)` and longer prefixes when practical.
- **CIDX-025** — The GUI Structure/Create Index flow SHALL allow selection and ordering of multiple columns, clearly showing the resulting key order before creation.
- **CIDX-026** — The CLI schema/index listing SHALL display composite columns in stored key order.
- **CIDX-027** — Index names, indexed column names, and UTF-8 TEXT values in composite keys SHALL obey the same UTF-8 safety requirements as their single-column equivalents.
- **CIDX-028** — Descending-per-column index definitions are NOT required in v1.0. If accepted syntactically, they SHALL be implemented correctly rather than ignored. The minimum mandatory implementation is ascending key order for every component.
- **CIDX-029** — Included/covering columns are NOT required. The implementation SHALL NOT claim a covering-index plan unless all requested values are actually obtainable without table-row access.
- **CIDX-030** — Composite primary keys are not required as SQL table declarations in v1.0; composite UNIQUE and nonunique secondary indexes are mandatory.

## 11. Schema Catalog

- **SCHEMA-001** — The database SHALL maintain a persistent schema catalog inside the database file.
- **SCHEMA-002** — The catalog SHALL describe tables, columns, types, nullability, defaults, primary keys, unique constraints, and indexes.
- **SCHEMA-003** — Schema object names SHALL be stored as UTF-8.
- **SCHEMA-004** — Table names and column names SHALL reject embedded NUL bytes.
- **SCHEMA-005** — Duplicate names within the same applicable namespace SHALL be rejected according to documented comparison rules.
- **SCHEMA-006** — Creating a table SHALL be transactional.
- **SCHEMA-007** — Dropping a table SHALL be transactional.
- **SCHEMA-008** — Creating an index SHALL be transactional and SHALL populate it from existing rows before commit.
- **SCHEMA-009** — Dropping an index SHALL be transactional.
- **SCHEMA-010** — `ALTER TABLE ... ADD COLUMN` SHALL be supported for nullable columns and/or columns having a constant default.
- **SCHEMA-011** — `ALTER TABLE ... RENAME TO` SHALL be supported.
- **SCHEMA-012** — Catalog corruption SHALL be detectable by `edb-check`.
- **SCHEMA-013** — Schema changes SHALL invalidate stale prepared/planned statements safely.
- **SCHEMA-014** — System catalog rows SHALL not be directly writable through ordinary user DML.
## 12. SQL Lexer and Parser

- **SQL-LEX-001** — The SQL lexer SHALL be implemented by the project and SHALL produce explicit token kinds with source offsets.
- **SQL-LEX-002** — The lexer SHALL handle ASCII whitespace plus line endings consistently.
- **SQL-LEX-003** — SQL keywords SHALL be case-insensitive in ASCII.
- **SQL-LEX-004** — Quoted string literals SHALL support escaping by doubled single quotes.
- **SQL-LEX-005** — Quoted identifiers SHALL be supported with one documented quoting style.
- **SQL-LEX-006** — Integer and floating literals SHALL detect overflow or malformed forms.
- **SQL-LEX-007** — Line comments beginning with `--` SHALL be supported.
- **SQL-LEX-008** — The lexer SHALL reject embedded NUL in SQL input unless the front end provides length-aware semantics and a documented rule.
- **SQL-PARSE-001** — The parser SHALL be authored manually using recursive descent, Pratt parsing, precedence climbing, or another project-authored technique.
- **SQL-PARSE-002** — Syntax errors SHALL report a useful byte offset or line/column location and an error category.
- **SQL-PARSE-003** — The parser SHALL construct an AST or equivalent structured representation; direct ad-hoc string splitting is forbidden.
- **SQL-PARSE-004** — Expression precedence SHALL be deterministic and tested.
- **SQL-PARSE-005** — Parenthesized expressions SHALL override normal precedence.
- **SQL-PARSE-006** — Multiple statements separated by semicolons SHALL be supported in batch input.
- **SQL-PARSE-007** — A syntax error SHALL not execute the malformed statement.

## 13. SQL Semantics and Type Rules

- **SEM-001** — NULL comparison SHALL follow documented SQL-style three-valued logic; `NULL = NULL` SHALL not evaluate TRUE.
- **SEM-002** — Division by zero SHALL produce a deterministic query error or documented NULL result; it SHALL never crash.
- **SEM-003** — Integer arithmetic overflow SHALL be detected or promoted according to one documented rule; signed C overflow SHALL not be relied upon.
- **SEM-004** — Numeric comparison between INTEGER and REAL SHALL be defined and tested.
- **SEM-005** — TEXT comparison SHALL use a documented deterministic collation. At minimum, binary UTF-8/code-point-safe ordering SHALL be available.
- **SEM-006** — An ASCII-only case-insensitive collation MAY be provided, but SHALL NOT claim full Unicode case folding unless fully implemented.
- **SEM-007** — `LIKE` wildcard matching SHALL operate without splitting UTF-8 continuation bytes. Chinese substring and wildcard matching SHALL work correctly.
- **SEM-008** — Invalid UTF-8 inserted into a TEXT value SHALL be rejected or normalized according to one documented rule; BLOB remains unrestricted.
- **SEM-009** — Column defaults SHALL be applied to omitted INSERT columns.
- **SEM-010** — NOT NULL constraints SHALL be enforced on INSERT and UPDATE.
- **SEM-011** — UNIQUE constraints SHALL be enforced using indexes or equivalently bounded lookup structures.
- **SEM-012** — PRIMARY KEY uniqueness SHALL be enforced transactionally.
- **SEM-013** — Constraint failure SHALL roll back the current statement without leaving partial index/table changes.
- **SEM-014** — ORDER BY SHALL have deterministic NULL placement defined by the project.
- **SEM-015** — LIMIT/OFFSET negative and overflow inputs SHALL have documented errors.
- **SEM-016** — DISTINCT SHALL treat NULL values according to one documented SQL-consistent rule.
## 14. Query Planner and Execution Engine

- **PLAN-001** — The executor SHALL operate on structured plans/operators rather than re-parsing SQL during row iteration.
- **PLAN-002** — The planner SHALL support full table scan.
- **PLAN-003** — The planner SHALL support primary-key point lookup.
- **PLAN-004** — The planner SHALL support secondary-index equality lookup.
- **PLAN-005** — The planner SHALL support secondary-index bounded range scan for compatible predicates.
- **PLAN-006** — The planner SHALL choose a usable index for simple conjunctions when a leading indexed column is constrained.
- **PLAN-007** — The planner SHALL support nested-loop join.
- **PLAN-008** — The planner SHALL support index-assisted nested-loop join when an applicable index exists.
- **PLAN-009** — ORDER BY MAY use an index when order compatibility is proven; otherwise it SHALL perform an explicit sort.
- **PLAN-010** — Sorting SHALL not compare raw pointers or rely on unstable address order for equal keys.
- **PLAN-011** — GROUP BY and aggregation SHALL be implemented by project-authored logic.
- **PLAN-012** — Planner decisions SHALL be visible through `EXPLAIN`.
- **PLAN-013** — `EXPLAIN` SHALL indicate at minimum scan type, chosen table/index, join order, sort step, and aggregation step where applicable.
- **PLAN-014** — `ANALYZE` SHALL collect persistent or reconstructible basic statistics useful to planning, at minimum row count and index cardinality estimate.
- **PLAN-015** — Planner behavior SHALL remain correct when statistics are absent or stale; statistics affect performance choice, not correctness.
- **PLAN-016** — Execution SHALL propagate cancellation/interruption from the front end at safe boundaries for long queries.
- **PLAN-017** — A cancelled read query SHALL not corrupt state.
- **PLAN-018** — A cancelled write statement SHALL roll back its statement changes.
- **PLAN-019** — Composite-index planning SHALL obey CIDX-013 through CIDX-019.
- **PLAN-020** — For index `(a,b,c)`, `a=? AND b=?` SHALL be representable as a bounded prefix seek; `b=?` alone SHALL not be presented as an equivalent seek.
- **PLAN-021** — For index `(a,b,c)`, equality constraints on `a,b` plus a range on `c` SHALL be representable as one ordered range scan when semantically compatible.
- **PLAN-022** — `EXPLAIN` output for composite indexes SHALL state seek prefix and range component so acceptance tests can distinguish a real composite seek from a full scan.
- **PLAN-023** — Planner cost/statistics logic SHALL never change query correctness when composite-prefix statistics are missing or stale.
## 15. Transactions and Atomicity

- **TXN-001** — Autocommit mode SHALL be supported.
- **TXN-002** — Explicit `BEGIN` SHALL start a transaction.
- **TXN-003** — `COMMIT` SHALL atomically make all changes in the transaction durable according to the durability mode.
- **TXN-004** — `ROLLBACK` SHALL discard all changes since BEGIN.
- **TXN-005** — SAVEPOINT SHALL create a nested rollback point within a transaction.
- **TXN-006** — ROLLBACK TO SHALL undo changes after the named savepoint without ending the outer transaction.
- **TXN-007** — RELEASE SHALL merge/remove the named savepoint according to documented semantics.
- **TXN-008** — Failed statements SHALL have statement-level atomicity inside a larger transaction.
- **TXN-009** — A constraint failure in one statement SHALL not automatically destroy previously successful statements in the same explicit transaction unless a documented fatal error occurs.
- **TXN-010** — Transaction state SHALL be observable by CLI prompt/status and GUI status indicator.
- **TXN-011** — Closing a connection with an active uncommitted transaction SHALL roll it back.
- **TXN-012** — An application crash before commit completion SHALL not expose a partially committed logical transaction after recovery.
- **TXN-013** — A successful durable COMMIT acknowledged to the caller SHALL survive a subsequent simulated abrupt termination under the defined crash model.
- **TXN-014** — Transaction identifiers or sequence numbers SHALL be monotonic enough to support WAL recovery ordering.
- **TXN-015** — Nested BEGIN without savepoint syntax SHALL return a deterministic error.
- **TXN-016** — Explicit transactions SHALL use the MVCC snapshot semantics defined in Section 17.1.
- **TXN-017** — A transaction SHALL read its own successful writes, updates, and deletes before commit.
- **TXN-018** — A transaction SHALL never read another transaction's uncommitted versions.
- **TXN-019** — Statement rollback and SAVEPOINT rollback SHALL correctly restore MVCC visibility and index state, including composite index entries.
- **TXN-020** — Transaction and commit-sequence counters SHALL use checked arithmetic; exhaustion/wraparound SHALL produce a controlled error rather than reuse an identifier unsafely.
## 16. Write-Ahead Log and Crash Recovery

- **WAL-001** — The engine SHALL implement a write-ahead log or journal designed by the project; simply copying the whole database for every transaction is not acceptable.
- **WAL-002** — WAL records SHALL have explicit record types, lengths, sequence information, and integrity checks.
- **WAL-003** — WAL records SHALL be parsed with bounds checks before use.
- **WAL-004** — Page changes required for recovery SHALL be represented sufficiently to redo or undo according to the chosen documented recovery design.
- **WAL-005** — Log durability ordering SHALL ensure required log data reaches durable storage before dependent main-file pages are considered committed.
- **WAL-006** — A commit record SHALL distinguish committed from incomplete transactions.
- **WAL-007** — Recovery SHALL run automatically when opening a database with pending recovery state.
- **WAL-008** — Recovery SHALL be idempotent: crashing during recovery and rerunning recovery SHALL converge to a valid state.
- **WAL-009** — Torn/truncated WAL tails SHALL be detected and handled without reading beyond valid records.
- **WAL-010** — Checksum failure inside the committed required portion of WAL SHALL produce a corruption/recovery error rather than silent acceptance.
- **WAL-011** — Checkpointing SHALL move recoverable committed state into the main database and allow obsolete WAL space to be reclaimed.
- **WAL-012** — Checkpoint SHALL be safe if interrupted.
- **WAL-013** — Checkpoint thresholds SHALL be deterministic/configurable within documented limits.
- **WAL-014** — The engine SHALL distinguish clean shutdown, recoverable dirty shutdown, and unrecoverable corruption states.
- **WAL-015** — Crash injection tests SHALL terminate a process at many named durability checkpoints.
- **WAL-016** — For each crash point, reopening SHALL produce either the complete pre-transaction state or complete committed post-transaction state according to whether durable commit had occurred; mixed state is forbidden.
- **WAL-017** — Recovery SHALL rebuild or validate indexes consistently with table state.
- **WAL-018** — No test may satisfy crash recovery merely by deleting the database and regenerating fixtures.
## 17. Concurrency and Locking

- **LOCK-001** — The engine SHALL support multiple concurrent read transactions against the same database file from independent connections/processes.
- **LOCK-002** — Version 1.0 permits at most one active write transaction at a time per database. Multiple concurrent writers are not required.
- **LOCK-003** — An active writer SHALL NOT invalidate or force-terminate readers whose snapshots began before the writer committed.
- **LOCK-004** — Existing read transactions SHALL continue to observe their stable snapshots while a writer creates and commits newer row versions.
- **LOCK-005** — A second writer SHALL use a bounded wait/timeout or return an explicit busy/locked result; it SHALL never enter an unsafe simultaneous-write state.
- **LOCK-006** — Ordinary row-level reads SHALL not require exclusive database locking for the whole read transaction.
- **LOCK-007** — Lock release SHALL occur on normal close and operating-system process termination.
- **LOCK-008** — Lock files/shared lock metadata, if used, SHALL not create a permanently stale writer or reader registration after an unclean process exit.
- **LOCK-009** — GUI and CLI SHALL surface locked/busy conditions distinctly from corruption, authentication, and SQL errors.
- **LOCK-010** — DDL and structural maintenance operations MAY require stronger schema/database locks. Their lock requirements SHALL be documented and behavior under active snapshots SHALL be deterministic.
- **LOCK-011** — Version 1.0 SHALL reject or wait for DDL/VACUUM/rekey operations that cannot safely coexist with active snapshots rather than silently violating snapshot semantics.
- **LOCK-012** — Automated tests SHALL use separate processes, not only multiple handles in one process, for mandatory concurrency acceptance scenarios.

### 17.1 Multi-Version Concurrency Control (MVCC)

MVCC is mandatory in v1.0. The required isolation level is **snapshot isolation with multiple concurrent readers and a single active writer**. A global read/write mutex that blocks every reader for the full duration of a writer is not an acceptable substitute.

#### 17.1.1 Snapshot Semantics

- **MVCC-001** — Every explicit transaction SHALL have a stable logical snapshot established at transaction start.
- **MVCC-002** — An autocommit read statement SHALL execute against a snapshot established for that statement.
- **MVCC-003** — Within one explicit transaction, repeated reads SHALL continue to use the same snapshot until COMMIT or ROLLBACK.
- **MVCC-004** — A transaction SHALL see versions committed before or at its snapshot boundary and SHALL not see versions committed after that boundary, except for its own writes.
- **MVCC-005** — A transaction SHALL see its own successful inserts and updates immediately.
- **MVCC-006** — A transaction SHALL treat its own successful deletes as absent immediately.
- **MVCC-007** — Uncommitted changes from any other connection/process SHALL never be visible.
- **MVCC-008** — A read transaction that begins before writer W commits SHALL continue seeing the pre-W logical state after W commits.
- **MVCC-009** — A new read transaction beginning after W's durable commit SHALL see W's committed state.
- **MVCC-010** — Snapshot isolation SHALL prevent dirty reads, non-repeatable reads caused by later commits, and phantoms caused solely by later committed inserts during one explicit transaction snapshot.
- **MVCC-011** — Serializable isolation and multiple simultaneous writers are not required by v1.0 and SHALL not be claimed unless separately implemented and tested.

#### 17.1.2 Version Representation and Visibility

- **MVCC-012** — Each logical row SHALL support multiple physical/logical versions when necessary to preserve active snapshots.
- **MVCC-013** — Every row version SHALL carry or resolve to creation-transaction/commit visibility metadata and retirement/deletion visibility metadata sufficient to decide snapshot visibility without consulting mutable user data.
- **MVCC-014** — An INSERT SHALL create a new uncommitted version belonging to the writer; it becomes visible to new transactions only after successful commit.
- **MVCC-015** — An UPDATE SHALL create a new row version and retire the prior visible version for future snapshots. It SHALL NOT destructively overwrite the only copy if an active older snapshot may still need it.
- **MVCC-016** — A DELETE SHALL retire/tombstone the visible version for future snapshots while preserving enough state for older active snapshots to continue reading it.
- **MVCC-017** — Aborted/rolled-back versions SHALL never become visible to other transactions.
- **MVCC-018** — Visibility decisions SHALL be centralized in project-authored MVCC logic; individual query operators SHALL NOT invent inconsistent visibility rules.
- **MVCC-019** — Table scans, primary-key lookups, secondary-index lookups, composite-index lookups, joins, aggregates, and GUI data browsing SHALL all apply the same MVCC visibility semantics.
- **MVCC-020** — If a physical row identifier changes across versions, references/index entries SHALL still resolve to the correct visible version without returning stale/deleted data.

#### 17.1.3 MVCC and Indexes

- **MVCC-021** — Secondary indexes, including composite indexes, SHALL preserve old logical index keys while an active snapshot can still require the corresponding old row version.
- **MVCC-022** — Updating an indexed key from `K_old` to `K_new` SHALL allow an older snapshot to find `K_old` and a post-commit snapshot to find `K_new`.
- **MVCC-023** — A post-commit lookup for `K_old` SHALL not return the updated row unless another currently visible row legitimately has that key.
- **MVCC-024** — Deleting a row SHALL not make its old index entry unusable to a snapshot that began before the delete commit.
- **MVCC-025** — Index scans MAY encounter entries that are not visible to the current snapshot, but they SHALL filter them correctly and SHALL not return duplicate logical row versions.
- **MVCC-026** — Unique-constraint checks SHALL consider the correct writer-visible/current committed state so a newly committed duplicate fully non-NULL unique tuple cannot be created.
- **MVCC-027** — Composite UNIQUE indexes SHALL combine CIDX-009 NULL semantics with MVCC visibility: obsolete versions invisible to the writer SHALL not create false uniqueness failures once safe visibility rules permit reuse of a key.
- **MVCC-028** — Index integrity checking SHALL be able to distinguish a valid retained historical entry from an orphan/stale corrupt entry.

#### 17.1.4 Transaction IDs, Commit Sequence, and Recovery

- **MVCC-029** — The engine SHALL maintain a monotonic 64-bit-or-wider transaction/commit sequencing mechanism sufficient to establish snapshot order.
- **MVCC-030** — Transaction identity and commit publication SHALL be integrated with WAL/recovery so recovery can classify versions as committed, aborted/incomplete, or otherwise safely reclaimable.
- **MVCC-031** — The durable commit boundary that makes a transaction visible to future snapshots SHALL correspond to the WAL durability rules; a transaction SHALL not become externally visible before the required durable commit state.
- **MVCC-032** — Crashing after durable commit but before version/index cleanup SHALL recover to the committed logical state while retaining/reclaiming historical versions safely.
- **MVCC-033** — Crashing before durable commit SHALL not expose the writer's new versions after recovery.
- **MVCC-034** — Recovery SHALL be idempotent even when historical MVCC versions and composite index entries are present.
- **MVCC-035** — A process that dies while holding a read snapshot SHALL not pin historical versions forever after operating-system cleanup/reopen.

#### 17.1.5 Version Garbage Collection

- **MVCC-036** — The engine SHALL track or derive the oldest active snapshot boundary needed by current readers.
- **MVCC-037** — A historical row/index version SHALL NOT be reclaimed while any active snapshot may still legally observe it.
- **MVCC-038** — Once no active snapshot can observe a retired/aborted historical version and recovery no longer requires it, the engine SHALL provide a path to reclaim its storage.
- **MVCC-039** — Version reclamation MAY occur incrementally and/or during VACUUM, but it SHALL be deterministic, integrity-checkable, and crash-safe.
- **MVCC-040** — Long-lived readers MAY delay reclamation but SHALL not cause incorrect results, use-after-free page references, or index corruption.
- **MVCC-041** — VACUUM SHALL either wait/reject while incompatible snapshots exist or preserve their required historical view; v1.0 permits explicit busy rejection.
- **MVCC-042** — Maintenance statistics SHALL expose at minimum active snapshot count (for the local process/available global mechanism), oldest visible snapshot/sequence if available, and reclaimable historical-version count or page estimate.

#### 17.1.6 Schema Changes and MVCC

- **MVCC-043** — Full multi-version schema catalogs are not required in v1.0.
- **MVCC-044** — DDL that would invalidate an active reader's schema SHALL acquire an exclusive schema condition and SHALL wait/fail with BUSY while incompatible active snapshots exist.
- **MVCC-045** — DDL SHALL never silently change column interpretation under an already-running read transaction.
- **MVCC-046** — GUI/CLI SHALL display a clear busy reason when DDL/VACUUM/rekey cannot proceed because of active snapshots.

#### 17.1.7 MVCC Diagnostics

- **MVCC-047** — Debug/check builds SHALL provide an internal consistency report for row-version chains or equivalent version structures.
- **MVCC-048** — `edb-check` SHALL validate version metadata ranges, version-chain cycles, impossible transaction ordering, references to nonexistent transaction state, and historical index/row consistency.
- **MVCC-049** — `EXPLAIN` need not expose physical version-chain details, but executor diagnostics in debug/test mode SHALL permit tests to prove an older snapshot returned an older version rather than a cached stale result.
- **MVCC-050** — Completion evidence SHALL report the maximum number of simultaneous reader processes exercised and the number of MVCC concurrency scenarios executed.
## 18. Authenticated Encryption

Encryption is a mandatory feature of the database format. The objective is to implement specified well-known primitives, not to invent a proprietary cipher.

- **CRYPTO-001** — The engine SHALL support password-protected databases.
- **CRYPTO-002** — Passwords SHALL be converted to key material using PBKDF2-HMAC-SHA-256 implemented by the project.
- **CRYPTO-003** — The KDF SHALL use a per-database random salt stored in the authenticated file header.
- **CRYPTO-004** — KDF iteration count SHALL be stored in the file header and validated against reasonable minimum/maximum bounds before work is performed.
- **CRYPTO-005** — Data pages and recovery records containing user/schema data SHALL be encrypted and authenticated using XChaCha20-Poly1305 implemented by the project.
- **CRYPTO-006** — XChaCha20 SHALL be derived using a project-authored HChaCha20 implementation.
- **CRYPTO-007** — Poly1305 SHALL be implemented by the project with correct modular arithmetic and validated using known-answer tests.
- **CRYPTO-008** — Every authenticated-encryption operation SHALL use a nonce that is unique for a given key.
- **CRYPTO-009** — Nonce construction/generation SHALL remain unique across page rewrites, transactions, checkpoints, process restarts, and recovery.
- **CRYPTO-010** — Random salts/nonces requiring entropy SHALL use an operating-system cryptographically secure random source, never `rand()` or time-based pseudo-random values.
- **CRYPTO-011** — Authentication tags SHALL be verified before decrypted plaintext is exposed to higher database layers.
- **CRYPTO-012** — Authentication failure SHALL abort access to the affected encrypted object and SHALL not return unauthenticated plaintext.
- **CRYPTO-013** — The plaintext password and derived keys SHALL not be printed in logs, diagnostics, crash reports, or GUI status text.
- **CRYPTO-014** — Key buffers SHALL be overwritten before release where practical and SHALL not be persisted as plaintext files.
- **CRYPTO-015** — Wrong password SHALL fail cleanly without modifying the database.
- **CRYPTO-016** — Tampering with an encrypted page SHALL be detected.
- **CRYPTO-017** — Tampering with authenticated header fields SHALL be detected.
- **CRYPTO-018** — Copying an encrypted page from a different database into this database SHALL be detected through authentication/context binding.
- **CRYPTO-019** — The project SHALL include known-answer tests for SHA-256, HMAC-SHA-256, PBKDF2-HMAC-SHA-256, ChaCha20/HChaCha20, Poly1305, and XChaCha20-Poly1305.
- **CRYPTO-020** — Base64, XOR, byte rotation, substitution tables, checksums without secret keys, or plain ChaCha20 without authentication SHALL NOT be presented as encryption.
## 19. Password and Rekey Operations

- **REKEY-001** — Creating an encrypted database SHALL require an explicit password from an interactive secure prompt or caller-provided API parameter; the password SHALL not be forced onto the command line.
- **REKEY-002** — The CLI SHALL provide a way to open encrypted databases without placing the password in shell history.
- **REKEY-003** — The GUI SHALL use a custom password dialog with masked input and explicit error state.
- **REKEY-004** — A `rekey` maintenance operation SHALL change the database password and fresh cryptographic salt/material.
- **REKEY-005** — Rekey SHALL be atomic at the database-file level: interruption SHALL not destroy the only valid copy.
- **REKEY-006** — Rekey SHALL not reuse encryption nonces from the old key under the new key.
- **REKEY-007** — An empty password policy SHALL be documented; if empty passwords are rejected, rejection SHALL be explicit.
- **REKEY-008** — The engine SHALL impose a maximum password byte length to prevent unreasonable allocation and SHALL document it.

## 21. Partial Corruption Recovery and Salvage

- **SALVAGE-001** — Salvage SHALL write to a separate output database by default.
- **SALVAGE-002** — Salvage SHALL never overwrite the damaged source unless an explicit option requests replacement after a successful output verification.
- **SALVAGE-003** — Valid independent tables/rows SHALL be recovered when their pages and required metadata are intact.
- **SALVAGE-004** — Rows depending on corrupted overflow chains SHALL be reported as unrecoverable rather than returned with invented/truncated data.
- **SALVAGE-005** — Index corruption MAY be repaired by rebuilding an index from valid table rows.

- **SALVAGE-007** — Catalog corruption that makes object identity ambiguous SHALL stop automatic destructive repair.
- **SALVAGE-008** — Salvage output SHALL pass the same full integrity checker.
- **SALVAGE-009** — Salvage SHALL produce a report of recovered objects, skipped objects, damaged page numbers, and reasons.
- **SALVAGE-010** — Corruption tests SHALL flip bits, truncate files, duplicate pages, alter child pointers, corrupt tags/checksums, and damage WAL tails.

## 27. Text Rendering and UTF-8 Handling

- **UTF8-008** — The query editor SHALL preserve tabs/newlines according to documented editing behavior.
- **UTF8-009** — Clipboard operations SHALL be length-aware and SHALL not truncate valid UTF-8 at arbitrary internal buffer limits without reporting it.
## 28. Memory Management and Defensive C Requirements

- **MEM-001** — Every allocation failure SHALL be handled as an error path; dereferencing a NULL allocation is forbidden.
- **MEM-002** — Size arithmetic for allocations, page offsets, row lengths, and result counts SHALL use overflow-checked operations.
- **MEM-003** — Ownership rules SHALL be clear for allocated pages, AST nodes, strings, values, plans, statements, and GUI objects.
- **MEM-004** — Error cleanup paths SHALL release resources already acquired.
- **MEM-005** — No function SHALL return pointers to expired stack storage.
- **MEM-006** — Buffers receiving formatted text SHALL use bounded operations or precomputed exact sizing.
- **MEM-007** — User-controlled length values SHALL not be passed unchecked to stack allocations.
- **MEM-008** — Recursive algorithms operating on corrupt on-disk structures SHALL have depth/cycle protection.
- **MEM-009** — SQL parser nesting SHALL have a documented finite limit or safe dynamic protection against stack exhaustion.
- **MEM-010** — The engine SHALL cap schema-name length, column count, maximum SQL statement length, maximum row/value length, and maximum expression depth with documented limits.
- **MEM-011** — Limits SHALL return explicit errors rather than wrap integers.
- **MEM-012** — Test builds SHOULD enable strong compiler warnings and SHALL contain no intentionally ignored warnings from project code under documented build flags.

## 34. Automated Testing Architecture

- **TEST-001** — `make test` SHALL build test binaries and execute the complete mandatory automated suite.
- **TEST-002** — `make check` SHALL include `make test` plus stricter static/runtime invariant checks available within the project.
- **TEST-003** — Tests SHALL be reproducible from a clean source checkout without requiring prebuilt database files not generated from checked-in fixture definitions.
- **TEST-004** — Test failures SHALL identify the failing test and expected/actual condition.
- **TEST-005** — A single failure SHALL cause an overall nonzero status even if later tests continue.
- **TEST-006** — Tests SHALL not modify source-controlled fixture definitions.
- **TEST-007** — Test temporary directories SHALL be isolated by test case or worker so stale files cannot create false success.
- **TEST-008** — At least one full end-to-end test SHALL create a database, define schema, insert data, query, index, update, delete, commit, close, reopen, verify, export, vacuum, and query again.

- **TEST-012** — A passing test suite SHALL contain no mandatory `skip`, `xfail`, TODO-only, disabled-by-default, or environment-silenced cases.
- **TEST-013** — Every randomized/model-based failure SHALL print a reproducible seed plus the minimal operation prefix known to reproduce the failure when practical.
- **TEST-014** — Concurrency tests SHALL include synchronization barriers so the intended transaction interleavings are deterministic rather than relying only on sleep timing.
- **TEST-015** — Tests that assert planner/index behavior SHALL inspect `EXPLAIN` or internal plan diagnostics in addition to checking result rows.
- **TEST-016** — Tests that assert MVCC behavior SHALL use at least two independent connections and mandatory process-level cases SHALL use separate OS processes.
- **TEST-017** — Test fixtures SHALL be regenerated from authored definitions during a clean test run; opaque prebuilt databases SHALL not be the sole source of expected state.
- **TEST-018** — The test summary SHALL list mandatory suite coverage by requirement family, including composite-index and MVCC cases.

### 34.5 Mandatory Composite-Index Acceptance Matrix

The following matrix is normative. Implementations MAY add cases but SHALL NOT remove these.

- **CIDXT-001** — Build `(a,b)` over an empty table; validate empty root/index metadata and reopen.
- **CIDXT-002** — Insert one tuple; point lookup by full tuple returns exactly one row.
- **CIDXT-003** — Insert many equal `a` values with varying `b`; prefix scan `a=?` returns exactly the matching ordered range.
- **CIDXT-004** — Insert many equal `(a,b)` values into a nonunique index; every row remains independently addressable and no entry overwrites another.
- **CIDXT-005** — Insert ascending tuple sequence until at least three B+ tree levels exist.
- **CIDXT-006** — Repeat CIDX-005 in descending tuple order.
- **CIDXT-007** — Repeat with deterministic pseudorandom tuple order and compare traversal with a reference sorted tuple list.
- **CIDXT-008** — Delete tuple patterns forcing leaf borrow-left and validate all remaining tuple scans.
- **CIDXT-009** — Delete tuple patterns forcing leaf borrow-right.
- **CIDXT-010** — Force merge-left, merge-right, internal merge, and root collapse with composite keys.
- **CIDXT-011** — Test `(INTEGER,TEXT)` keys around negative/zero/positive numbers and Chinese UTF-8 strings.
- **CIDXT-012** — Test `(TEXT,TEXT)` keys that would collide under naive delimiter-free concatenation.
- **CIDXT-013** — Test `(BLOB,INTEGER)` with embedded NUL and all byte values in BLOB components.
- **CIDXT-014** — Test NULL in each component position and combinations of multiple NULL components.
- **CIDXT-015** — UNIQUE `(a,b)` rejects duplicate `(1,2)` while permitting the mandatory NULL-containing non-conflicting cases.
- **CIDXT-016** — A uniqueness failure after a page split/rebalance opportunity leaves both table and every index structurally unchanged after statement rollback.
- **CIDXT-017** — Update only first component; old full-tuple seek disappears for new snapshots and new seek appears.
- **CIDXT-018** — Update only second/middle component with same guarantees.
- **CIDXT-019** — Update several components in one statement affecting many rows; statement is all-or-nothing on constraint failure.
- **CIDXT-020** — Delete all rows sharing one leading prefix and verify neighboring prefix ranges remain intact.
- **CIDXT-021** — `WHERE a=?` on `(a,b,c)` uses a prefix seek and returns reference-model rows.
- **CIDXT-022** — `WHERE a=? AND b=?` uses a longer prefix seek.
- **CIDXT-023** — `WHERE a=? AND b=? AND c>=? AND c<?` uses equality prefix plus bounded final range.
- **CIDXT-024** — `WHERE b=?` on `(a,b,c)` SHALL not claim an ordered direct seek on that index.
- **CIDXT-025** — `WHERE a>? AND b=?` SHALL not falsely claim `b` narrows each position after the first range unless an explicitly stronger correct plan is implemented.
- **CIDXT-026** — Compatible `ORDER BY a,b,c` avoids explicit sort when planner chooses the index; incompatible ordering retains a sort.
- **CIDXT-027** — Join using equality on the first two components of inner `(a,b,c)` can use index-assisted nested-loop and matches full-scan reference results.
- **CIDXT-028** — Drop/recreate composite index on populated table preserves query results.
- **CIDXT-029** — `ANALYZE` then reopen preserves/reconstructs statistics without changing results.
- **CIDXT-030** — Oversized serialized composite key fails before persistent mutation.
- **CIDXT-031** — Crash before composite-index creation commit leaves no partially visible index.
- **CIDXT-032** — Crash after durable composite-index creation commit recovers the complete valid index.
- **CIDXT-033** — Index rebuild from a deliberately damaged source index recreates keys from table rows and passes `edb-check`.
- **CIDXT-034** — VACUUM and rekey each preserve tuple ordering, uniqueness, and EXPLAIN usability.
- **CIDXT-035** — GUI Create Index can create `(category,priority,deadline)` in that exact order; Structure view and CLI both display the same order.

### 34.6 Mandatory MVCC Interleaving Matrix

Tests SHALL use explicit barriers/events/pipes or equivalent deterministic synchronization. Merely sleeping for guessed durations is insufficient for these mandatory cases.

- **MVCCT-001** — R1 begins; R1 reads value `v0`; W updates to `v1` and commits; R1 reads again and still sees `v0`; R2 begins after commit and sees `v1`.
- **MVCCT-002** — R1 begins; W inserts row X and commits; repeated R1 predicate/range query does not gain X; R2 sees X.
- **MVCCT-003** — R1 begins; W deletes X and commits; R1 still sees X; R2 does not.
- **MVCCT-004** — W inserts X but has not committed; R1/R2 SHALL not see X; W sees X; after commit new reader sees X.
- **MVCCT-005** — W updates X but rolls back; no other reader ever sees the uncommitted version and post-rollback state is original.
- **MVCCT-006** — W deletes X but rolls back; row remains for all post-rollback readers.
- **MVCCT-007** — SAVEPOINT: W updates X to `v1`, savepoint, updates to `v2`, rollback-to; W sees `v1`; commit publishes `v1` only.
- **MVCCT-008** — An old snapshot survives a writer checkpoint and still reads its old logical state.
- **MVCCT-009** — An old snapshot survives a writer updating a single-column indexed key; old index seek works for R1, new key works for R2.
- **MVCCT-010** — Same as MVCCT-009 for a composite index where one leading component changes.
- **MVCCT-011** — Same as MVCCT-010 where a non-leading component changes.
- **MVCCT-012** — Writer deletes indexed row; old reader's index scan still returns it exactly once, new reader returns none.
- **MVCCT-013** — Writer inserts a duplicate nonunique composite tuple; old reader sees old multiplicity, new reader sees increased multiplicity.
- **MVCCT-014** — UNIQUE composite constraint is checked against correct writer-visible state and cannot be bypassed using invisible historical versions.
- **MVCCT-015** — Eight readers begin on the same state, writer commits a deterministic batch, all eight retain the old snapshot, then eight new readers see the new state.
- **MVCCT-016** — A second writer attempts BEGIN/write while W1 is active and receives the defined BUSY/timeout without changing file bytes logically.
- **MVCCT-017** — Reader process is killed while pinning old version; after cleanup/reopen/reclamation the version becomes reclaimable and no stale lock/snapshot remains.
- **MVCCT-018** — Long-lived reader blocks/rejects VACUUM according to specified policy; reader remains correct; VACUUM succeeds after reader ends.
- **MVCCT-019** — Long-lived reader blocks/rejects incompatible DDL; schema remains unchanged until safe.
- **MVCCT-020** — Rekey under incompatible active snapshot follows explicit busy policy without modifying password/file state.
- **MVCCT-021** — Crash writer before durable commit while R1 holds old snapshot; recovery/new reader observes pre-write state.
- **MVCCT-022** — Crash writer after durable commit while R1 existed in another surviving process; surviving R1 retains old snapshot if architecture supports continued access, while a reopened/new reader observes committed state. If process/file-recovery architecture necessarily invalidates surviving handles, the engine SHALL return a deterministic connection-invalidated error rather than mixed data; this exception SHALL be documented and tested.
- **MVCCT-023** — Crash during recovery with retained historical versions; repeated recovery converges and `edb-check` passes.
- **MVCCT-024** — Writer commits 100 sequential updates while R1 remains open; R1 sees initial version, latest reader sees update 100, and version storage remains valid.
- **MVCCT-025** — End R1 then run reclamation; historical versions no longer needed are reclaimed and logical current result is unchanged.
- **MVCCT-026** — Reader executes JOIN while writer changes joined rows; entire explicit reader transaction obeys its original snapshot.
- **MVCCT-027** — Reader executes GROUP BY/aggregate before and after writer commit inside same transaction and receives identical logical snapshot result.
- **MVCCT-028** — Reader uses composite prefix range before and after writer inserts keys inside that range; old snapshot range remains unchanged.
- **MVCCT-029** — Close connection with active writer transaction; rollback removes its versions and index entries.
- **MVCCT-030** — Process termination with active uncommitted writer is recovered as aborted/incomplete; no dirty version is visible.
- **MVCCT-031** — Wrong-password/open failure never registers a persistent snapshot or writer state.
- **MVCCT-032** — Allocation/I/O failure during version creation causes statement/transaction failure according to scope and never exposes half-linked chains.
- **MVCCT-033** — Allocation/I/O failure during index-version update cannot create row/index visibility disagreement.
- **MVCCT-034** — Version chain integrity report shows expected historical count before reclamation and reduced count after safe reclamation.
- **MVCCT-035** — Oldest-active-snapshot metric advances only after the oldest reader ends.

## 37. Performance and Scalability Floors

These are engineering floors intended to prevent obviously non-scalable substitutions. They are not absolute hardware performance benchmarks.

- **PERF-001** — The engine SHALL correctly store and query at least 100,000 rows in a table.
- **PERF-002** — An indexed equality lookup on a 100,000-row table SHALL use the B+ tree index according to EXPLAIN and SHALL not report a full table scan.
- **PERF-003** — A bounded indexed range query SHALL use an index where compatible.
- **PERF-004** — The GUI data grid SHALL remain usable on a 100,000-row table by fetching/virtualizing bounded result windows rather than constructing 100,000 independent widgets.
- **PERF-005** — Importing a large CSV SHALL process incrementally and SHALL not require loading the entire file into one in-memory string.
- **PERF-006** — Exporting large query results SHALL stream rows rather than requiring the complete result set in memory.
- **PERF-007** — Integrity checking MAY be linear in database size but SHALL operate with bounded memory relative to file size except for explicitly documented reachability structures.
- **PERF-008** — VACUUM MAY require a second database-sized temporary file but SHALL not require holding the full database in RAM.
- **PERF-009** — B+ tree operations SHALL have logarithmic search structure behavior rather than mandatory full scan per indexed operation.
- **PERF-010** — Parser and lexer SHALL be linear/bounded for ordinary inputs and protected against pathological nesting limits.
- **PERF-011** — On a 100,000-row table with index `(category,priority,deadline)`, a selective query constraining `category` and `priority` SHALL use the composite prefix index according to EXPLAIN rather than full scan.
- **PERF-012** — Holding eight read snapshots SHALL not require duplicating the entire database file per reader.
- **PERF-013** — One row update under MVCC SHALL not copy the entire database file as its normal versioning mechanism.
- **PERF-014** — Historical-version storage growth MAY be proportional to changed data while snapshots are held; it SHALL be reclaimable after snapshots end.
- **PERF-015** — MVCC visibility checks SHALL not require scanning every historical version in the database for each returned row; lookup SHALL be bounded to the relevant row/version chain or equivalent indexed metadata.
## 38. Resource and Failure Injection

- **FAIL-001** — Tests SHALL exercise simulated allocation failure at multiple internal allocation sites using a test allocator hook.
- **FAIL-002** — Allocation failure SHALL not leave a committed transaction half-applied.
- **FAIL-003** — Tests SHALL simulate short reads/writes or injected I/O failures through an internal I/O abstraction in test builds.
- **FAIL-004** — I/O failure during transaction commit SHALL return failure and preserve recoverable state.
- **FAIL-005** — I/O failure during VACUUM/rekey SHALL preserve the original valid file until safe replacement.
- **FAIL-006** — Tests SHALL exercise full-disk-like write failure through injection without needing to actually fill the filesystem.

## 41. Required Command-Level Acceptance Scenarios

- **ACC-A01** — **Create encrypted DB:** Create a new encrypted database; create `tasks`; insert Chinese and ASCII rows; commit; close; reopen with correct password; verify exact rows.
- **ACC-A02** — **Wrong password:** Attempt to open A01 with a wrong password; opening fails; database bytes are unchanged.
- **ACC-A03** — **Basic CRUD:** Insert, update, select, delete across reopen; verify indexes and row counts.
- **ACC-A04** — **Index split:** Insert enough indexed keys to produce a multilevel B+ tree; verify point and range queries plus integrity check.
- **ACC-A05** — **Index delete rebalance:** Delete patterns forcing borrow/merge/root collapse; verify exact remaining keys and integrity.
- **ACC-A06** — **Unique rollback:** Perform multi-row write where a uniqueness violation occurs; verify statement atomicity and unchanged valid prior rows.
- **ACC-A07** — **Explicit rollback:** Modify multiple tables then ROLLBACK; close/reopen; verify original committed state.
- **ACC-A08** — **Savepoints:** Apply nested savepoints, rollback one, release another, commit; verify expected mixed retained/undone actions.
- **ACC-A09** — **Crash before commit:** Kill during transaction before durable commit; recover; verify pre-transaction state.
- **ACC-A10** — **Crash after durable commit:** Kill after commit is durably recorded but before normal cleanup; recover; verify post-transaction state.
- **ACC-A11** — **Crash during checkpoint:** Kill at each checkpoint injection point; reopen repeatedly; verify convergent valid state.
- **ACC-A12** — **Large value:** Store/retrieve/update/delete >=1 MiB TEXT and BLOB values; verify checksums and overflow cleanup.
- **ACC-A13** — **Join aggregate:** Execute INNER/LEFT joins, GROUP BY, HAVING, aggregate functions over deterministic fixture; compare expected results.
- **ACC-A14** — **Planner:** Create alternate indexes/statistics; use EXPLAIN to prove point/range/index-assisted join choices.
- **ACC-A15** — **CSV round trip:** Export data with commas, quotes, embedded newlines, NULL, empty string, Chinese; import into new DB; compare logical values.
- **ACC-A16** — **Dump round trip:** Dump schema/data to SQL; rebuild new DB; compare schemas and rows.
- **ACC-A17** — **Vacuum:** Create bloat through insert/delete; VACUUM; verify file reduction when reclaimable and exact logical equivalence.
- **ACC-A18** — **Tamper page:** Flip a ciphertext/tag bit; open/check detects authentication/corruption and does not return forged row.
- **ACC-A19** — **Index corruption repair:** Corrupt only a rebuildable secondary index; checker diagnoses; repair rebuilds; all rows preserved.
- **ACC-A20** — **Partial salvage:** Damage one data region while leaving independent table intact; salvage to new DB; verify recovered set and explicit loss report.
- **ACC-A21** — **Rekey:** Rekey encrypted DB; old password fails; new password succeeds; logical data unchanged.
- **ACC-A22** — **Locking:** Start writer process; second conflicting writer gets busy/timeout rather than corrupting state.
- **ACC-A23** — **GUI end-to-end:** Create/open DB, create table, insert row, query it, edit it, integrity check and close through GUI only.
- **ACC-A24** — **GUI error recovery:** Trigger SQL error and constraint error in GUI; correct input and continue without restarting.
- **ACC-A25** — **Unicode:** Use Chinese table data and search/LIKE/export/reopen; verify byte-preserving valid UTF-8 behavior.
- **ACC-A26** — **LOC utility:** Run locscan over a fixture tree containing authored files and generated/binary decoys; verify exact classified totals.
- **ACC-A29** — **Composite index creation:** Create `(category, priority, deadline)` on populated data; reopen; CLI/GUI/catalog preserve order; integrity check passes.
- **ACC-A30** — **Composite prefix planning:** EXPLAIN proves usable seeks for leading prefixes and refuses false seek for non-leftmost-only predicate.
- **ACC-A31** — **Composite range:** Equality prefix plus final range returns exactly reference rows in key order.
- **ACC-A32** — **Composite unique/NULL:** Fully non-NULL duplicate fails atomically; required NULL-containing tuples coexist.
- **ACC-A33** — **Composite update/crash:** Update multiple key components across many rows and crash at mandatory WAL points; recovery yields all-old or all-new committed logical index/table state.
- **ACC-A34** — **MVCC stable reader:** Old reader spans writer commit and continues reading old value; new reader sees new value.
- **ACC-A35** — **MVCC insert/delete phantom protection:** Explicit old reader repeats range query across writer insert/delete commits and retains identical snapshot result.
- **ACC-A36** — **MVCC indexed history:** Old/new readers use an index after indexed-key update and each sees the correct historical/current key.
- **ACC-A37** — **MVCC composite history:** Same as A36 for composite indexed key, including leading-component change.
- **ACC-A38** — **Concurrent readers:** Eight separate reader processes retain one snapshot while writer commits; eight later readers see committed state.
- **ACC-A39** — **Single writer:** Second writer cannot enter unsafe write state and reports BUSY/timeout.
- **ACC-A40** — **Version GC:** Retired versions remain while needed, then are reclaimed after oldest reader ends; database remains logically identical and checker-clean.
- **ACC-A41** — **Killed reader cleanup:** Kill snapshot-holding process; prove it no longer pins reclamation permanently.
- **ACC-A42** — **MVCC crash before/after commit:** Crash runner demonstrates invisible pre-commit versions and durable post-commit visibility with consistent indexes.
- **ACC-A43** — **DDL/maintenance snapshot safety:** DDL/VACUUM/rekey follows documented BUSY/wait policy while incompatible reader exists and leaves file unchanged when rejected.
- **ACC-A44** — **MVCC corruption diagnostics:** Inject mandatory version-chain/transaction/index-history corruptions and verify exact checker error families.
