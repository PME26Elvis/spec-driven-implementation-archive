# 22 — Physics Inspector, Event Trace, Collision Trace, and Determinism Comparison

This document defines required diagnostic capabilities. These are real product engineering features, not test-only fake output.

## 1. Diagnostic principle

Diagnostics SHALL expose production runtime data originating from the same simulation/event structures used during Play/headless execution.

Hard-coded fixture-specific output, reconstructed values unrelated to runtime state, or a separate diagnostic-only solver is prohibited.

## 2. Existing Physics Inspector extension

The selected-ball Inspector SHALL continue to show the v0.1 fields and additionally expose:

- runtime ID;
- current fixed step;
- position;
- velocity;
- speed;
- radius/mass;
- current containing Sensor IDs;
- captured Kickout ID if any;
- last solid contact object/runtime ID;
- last normal/tangent impulse;
- last contact normal;
- last contact relative normal speed;
- cumulative collision count;
- cumulative CCD impact count;
- current deterministic state fingerprint excerpt.

## 3. Event Trace

The application SHALL provide a toggleable Event Trace view or panel.

Each record includes:

- monotonically increasing trace sequence number;
- fixed step index;
- sub-step time when applicable;
- source object ID;
- ball runtime ID when applicable;
- trigger type;
- event ID;
- action index/type;
- target ID when applicable;
- concise result/status;
- score before/after for score actions;
- causal parent sequence when generated by another action.

## 4. Event Trace order

Displayed/exported Event Trace order SHALL exactly match production action execution order.

Filtering/sorting in UI MAY change presentation only if user explicitly chooses it; exported canonical trace remains execution order.

## 5. Event Trace capacity

The live UI SHALL retain at least the newest 10,000 event-trace records.

When capacity is exceeded:

- discard oldest live UI records;
- increment dropped-trace-record counter;
- simulation behavior remains unchanged.

Headless trace export may stream records to avoid this UI retention limit.

## 6. Event Trace filters

Required filters:

- trigger type;
- source object ID substring;
- target object ID substring;
- ball runtime ID;
- fixed-step range.

Filtering SHALL NOT mutate simulation state.

## 7. Collision Trace

For a selected ball, the application SHALL retain at least the newest 256 collision/contact records.

Each record includes:

- fixed step;
- sub-step TOI;
- other entity ID/type;
- contact class;
- contact point;
- contact normal;
- pre-contact relative normal velocity;
- restitution/friction used;
- normal impulse;
- tangential impulse;
- post-contact ball velocity;
- CCD flag;
- active-source impulse contribution when bumper/slingshot/flipper applies energy.

## 8. Collision trace for ball-ball contacts

A ball-ball contact appears in both involved balls' trace histories with matching pair/contact identifiers. Normals are opposite under each ball's perspective.

## 9. Trace clearing

User may clear visible trace history. Clearing diagnostics:

- does not reset physics counters;
- does not alter replay state;
- does not dirty authored scene;
- is not Undoable.

Starting a fresh simulation clears prior session trace unless an explicit export is retained externally.

## 10. Trace export

Event and collision traces SHALL be exportable as UTF-8 line-oriented JSON or one valid JSON document. Exact file extension is implementation-defined.

Each export SHALL include:

- application version;
- physics behavior version;
- scene semantic fingerprint;
- fixed timestep;
- replay seed where relevant;
- trace schema version.

## 11. Headless trace switches

Headless mode SHALL support enabling event trace and collision trace without opening X11.

Trace output destination must be selectable independently from normal final-state JSON.

## 12. Determinism comparison utility

Required engineering utility capability: compare two deterministic checkpoint/trace outputs and locate first divergence.

The utility MAY be a mode of `simcheck` or a separate executable; the required capability name in reports is `detcompare`.

## 13. Comparison canonicalization

Comparison uses canonical entity ordering and numeric tolerance rules from runtime/replay specs.

It SHALL NOT compare irrelevant metadata such as wall-clock execution duration, filesystem path, or UI settings.

## 14. Comparison output

For equal traces:

- return success;
- report compared checkpoint/step span;
- report matching final fingerprint.

For divergence:

- return non-zero;
- first divergent fixed step;
- path-like field identifier, e.g. `balls[3].velocity.y`;
- entity ID;
- expected/left value;
- actual/right value;
- numeric deltas;
- prior matching fingerprint;
- divergent fingerprints.

## 15. Determinism bisection

The utility SHALL support efficient first-divergence location using available checkpoints rather than requiring the reviewer to inspect full traces manually. Linear scan is acceptable for bounded acceptance traces if it still reports the true first mismatch.

## 16. Scene Statistics Panel

The application SHALL provide a Scene Statistics surface accessible in Edit Mode and Play Mode.

Edit statistics:

- object count by type;
- group count;
- layer count;
- event count;
- event action count;
- enabled/disabled authored objects;
- locked objects;
- world dimensions;
- approximate serialized scene size after canonical serialization;
- validation Error/Warning count.

Play statistics additionally include:

- active/free/captured ball counts;
- solid collision count;
- CCD impact count;
- Sensor trigger count;
- event-action executions;
- current score/combo/multiplier;
- current turn;
- Tilt meter/state;
- current simulation step/time;
- dropped real-time backlog counter;
- latest render frame time and fixed steps executed for the previous rendered frame.

## 17. Statistics correctness

Statistics SHALL derive from production scene/runtime data. Counts must update within one rendered frame after relevant state changes.

Statistics panel is view-only and does not dirty scene.

## 18. No Diagnostics Center requirement

v1.0.0 does not require a general persistent Diagnostics Center. Errors/warnings continue to use the specified validation/error surfaces. The trace/statistics features in this document are specifically scoped and must not be interpreted as requiring feature proposal 42.

## 19. No Ghost Trajectory requirement

v1.0.0 does not require predicted or ghost trajectories. Implementations MAY add one as an extra feature, but it carries no acceptance credit and cannot replace collision/event tracing. This explicitly excludes feature proposal 45 from mandatory scope.

## 20. Acceptance evidence

Required evidence includes:

- screenshot of populated Event Trace;
- screenshot of selected-ball Collision Trace;
- exported trace from canonical event chain;
- `detcompare` equal result;
- `detcompare` deliberately modified trace identifying exact first divergence;
- Scene Statistics in Edit and Play modes.
