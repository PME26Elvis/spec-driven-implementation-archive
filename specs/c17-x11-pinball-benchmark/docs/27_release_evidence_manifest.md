# 27 — Release Evidence Manifest and Requirement-to-Proof Contract

## 1. Purpose

A release may not mark requirements PASS merely because the implementation claims they work. v1.0.0 requires machine-readable mapping from mandatory requirements to concrete proof.

## 2. Required file

Final delivery SHALL contain `RELEASE_EVIDENCE.json` conforming to `schemas/release_evidence_schema.json` from this task package.

## 3. Requirement entry

Every stable requirement ID in `14_traceability_matrix.md` SHALL appear exactly once in the evidence manifest.

Each entry includes:

- `requirement_id`;
- status;
- verification methods;
- referenced test IDs;
- referenced fixture IDs;
- referenced visual evidence IDs;
- referenced report/artifact paths;
- optional concise notes.

## 4. Status values

Allowed:

- `PASS`;
- `FAIL`;
- `BLOCKED`;
- `NOT_RUN`.

`SKIP` is not a valid completion status for mandatory requirements.

## 5. PASS rules

A PASS entry SHALL contain at least one evidence reference appropriate to the requirement.

Examples:

- deterministic physics: automated test + canonical fixture/checkpoint;
- UI animation: state test + transition evidence;
- save failure: fault-injection automated test;
- visual layout: screenshot evidence;
- dependency restriction: build/link audit evidence.

A note saying "implemented" is not evidence.

## 6. Evidence existence

Every referenced relative path SHALL exist in final delivery unless the reference identifies an in-report test ID rather than a file.

Every referenced screenshot/transition ID SHALL be declared in `VISUAL_EVIDENCE.md`.

Every test ID SHALL be present in machine-readable test summary.

## 7. Test identity

Mandatory tests SHALL have stable unique IDs, not only display names. Recommended form:

`T-<DOMAIN>-<NUMBER>`

Examples:

- `T-PHY-001`;
- `T-ED-042`;
- `T-IO-031`;
- `T-UI-015`.

## 8. Fixture identity

Acceptance fixtures use stable IDs from scenario/fixture manifest. A custom generated fixture used as evidence must be checked into final test fixtures or reproducibly generated by delivered test code.

## 9. Visual evidence identity

v1.0.0 expands static/transition evidence IDs. Required IDs are enumerated in `10_visual_acceptance.md`.

Evidence manifest references exact IDs rather than arbitrary filenames only.

## 10. Gate aggregation

`RELEASE_RESULT.json` gate PASS SHALL be consistent with all requirements assigned to that Gate. If any mandatory requirement in a Gate is FAIL/BLOCKED/NOT_RUN, Gate cannot be PASS.

## 11. Contradiction detection

Release validation utility SHALL detect at least:

- missing requirement entry;
- duplicate requirement entry;
- unknown requirement ID;
- PASS with no proof reference;
- referenced missing path;
- referenced unknown test ID;
- referenced unknown visual ID;
- Gate marked PASS while member requirement not PASS;
- overall complete=true while any mandatory Gate not PASS.

## 12. Integrity

The evidence manifest is not required to cryptographically sign artifacts, but deliberate fabrication/misreference is an Anti-placeholder Gate failure.

## 13. Self-verification utility

Required utility capability name: `releasecheck`.

It SHALL validate:

- `RELEASE_RESULT.json` schema;
- `RELEASE_EVIDENCE.json` schema;
- requirement coverage;
- referenced evidence existence;
- gate/status consistency;
- version consistency across required reports.

## 14. Human readability

Machine-readable evidence does not replace `RELEASE_CHECKLIST.md` or `TEST_REPORT.md`. Those remain required concise human summaries.

## 15. Completion rule

The implementation may be described as complete only when `releasecheck` passes and every mandatory requirement and Gate is PASS.
